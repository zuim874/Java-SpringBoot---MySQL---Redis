## 一、为什么需要重构？

### 1.1 "能跑就行"的问题

项目初期，目标是快速实现功能，代码难免会有一些"将就"的地方：

- **能用，但不规范**——比如 Java 字段用蛇形命名
- **能用，但冗余**——比如两套 SQL 注入防护同时存在
- **能用，但难维护**——比如一个 Controller 里混杂管理员和普通用户的操作

这些"将就"在项目规模小时没问题，但随着功能增加，维护成本会越来越高。

### 1.2 重构的目标

```
重构前（能跑）         重构后（规范）
├── 代码能用           ├── 代码规范
├── 结构混乱           ├── 结构清晰
├── 有重复代码         ├── 职责单一
├── 难扩展             ├── 易于维护
└── 不利于团队协作      └── 符合企业标准
```

## 三、Issue 1：Java 实体字段命名规范

### 3.1 问题现象

查看 `Role.java`：

```java
// 重构前：蛇形命名
@TableName("sys_role")
public class Role {
    private String role_code;    // 蛇形
    private String role_name;    // 蛇形
    private LocalDateTime create_time;  // 蛇形
    private LocalDateTime update_time;  // 蛇形
}
```

### 3.2 为什么这是问题？

MyBatis-Plus 默认开启 **`mapUnderscoreToCamelCase`**（下划线转驼峰）。

当从数据库查询时，处理流程如下：

```
数据库列：role_code
    ↓ mapUnderscoreToCamelCase 转换
驼峰属性：roleCode
    ↓ 查找 Java 字段
找不到 roleCode（只有 role_code），赋值失败 → role_code = null
```

**这就是之前 `User.java` 中 `user_role` 始终为 null 的根本原因！**

### 3.3 修改方案

**原则：Java 字段永远用驼峰命名，用 `@TableField` 注解映射数据库列名。**

```java
// 重构后：驼峰命名 + @TableField 显式映射
@TableName("sys_role")
public class Role {
    @TableField("role_code")
    private String roleCode;        // 驼峰

    @TableField("role_name")
    private String roleName;        // 驼峰

    @TableField("create_time")
    private LocalDateTime createTime;  // 驼峰

    @TableField("update_time")
    private LocalDateTime updateTime;  // 驼峰
}
```

### 3.4 为什么 `@TableField` 能解决问题？

`@TableField("role_code")` 告诉 MyBatis-Plus："这个 Java 字段映射到数据库的 `role_code` 列"。

```
MyBatis-Plus 处理流程：
1. 看到 @TableField("role_code") 注解
2. 跳过 mapUnderscoreToCamelCase 转换
3. 直接把 role_code 列的值赋给 roleCode 字段
```

**记忆口诀：Java 字段用驼峰，数据库列用蛇形，@TableField 做桥梁。**

### 3.5 受影响的范围

同一问题在 `User.java` 中也存在，之前已修复（见 `奇怪的问题：管理员权限无法正确识别.txt`）。

| 字段 | 原命名 | 新命名 | @TableField |
|------|--------|--------|-------------|
| 角色 | `user_role` | `userRole` | ✅ |
| 创建时间 | `create_time` | `createTime` | ✅ |
| 更新时间 | `update_time` | `updateTime` | ✅ |
| 最后登录 | `last_login_time` | `lastLoginTime` | ✅ |

## 四、Issue 2：空壳 Service 类

### 4.1 问题现象

重构前的 `RoleService.java`：

```java
@Service
public class RoleService {
    @Autowired
    private UserMapper userMapper;  // ❌ 角色Service注入用户Mapper
}
```

### 4.2 问题分析

1. **注入错误**：`RoleService` 应该操作用户角色，但注入的是 `UserMapper`（用户数据访问）
2. **空壳无用**：没有任何方法，这个类存在但没有提供任何价值
3. **违背单一职责**：角色相关的逻辑应该用 `RoleMapper`，而不是 `UserMapper`

### 4.3 修改方案

```java
@Service
public class RoleService {

    @Autowired
    private RoleMapper roleMapper;  // ✅ 注入正确的 Mapper

    /**
     * 根据角色编码查询
     */
    public Role findByCode(String roleCode) {
        QueryWrapper<Role> wrapper = new QueryWrapper<>();
        wrapper.eq("role_code", roleCode);
        return roleMapper.selectOne(wrapper);
    }

    /**
     * 查询所有可用角色
     */
    public List<Role> findAllActive() {
        QueryWrapper<Role> wrapper = new QueryWrapper<>();
        wrapper.eq("status", 1);
        return roleMapper.selectList(wrapper);
    }
}
```

### 4.4 学到什么？

**每个 Service 只关心自己对应的 Mapper：**

```
UserService  → UserMapper     （用户业务 → 用户数据）
RoleService  → RoleMapper     （角色业务 → 角色数据）
```

这叫"**数据访问层对应**"——服务层和数据访问层保持一一对应关系，避免跨层调用混乱。

## 五、Issue 3：重复的安全防护

### 5.1 问题现象

项目中有两套 SQL 注入防护：

**第一套：`GlobalSafeFilter.java`（Servlet 过滤器）**

```java
@WebFilter("/*")
public class GlobalSafeFilter implements Filter {
    // 检查请求参数中是否包含危险字符
    // 使用 @WebFilter 注解，由 @ServletComponentScan 自动注册
}
```

**第二套：`SqlInjectSafeInterceptor.java`（Spring 拦截器）**

```java
public class SqlInjectSafeInterceptor implements HandlerInterceptor {
    // 做同样的事：检查请求参数中是否包含危险字符
    // 由 WebMvcConfig 手动注册
}
```

### 5.2 为什么这是问题？

1. **功能完全重复**：两段代码做一模一样的事
2. **维护成本翻倍**：改一处还要记得改另一处
3. **实现方式不同，行为可能不一致**：一个正则表达式改了，另一个没改，导致行为差异
4. **混淆项目结构**：`common` 包下混杂通用组件和安全组件

### 5.3 两种方式的区别

| 对比项 | Servlet 过滤器 (`@WebFilter`) | Spring 拦截器 (`HandlerInterceptor`) |
|--------|-------------------------------|--------------------------------------|
| 层级 | 最底层，在 Spring 处理前 | Spring MVC 内部 |
| 注册方式 | `@WebFilter` + `@ServletComponentScan` | `WebMvcConfigurer.addInterceptors()` |
| 控制粒度 | 只能按 URL 路径 | 可以按路径、可以访问 Handler 对象 |
| 能否访问 Spring 容器 | 不能（除非特殊处理） | 能（可以注入其他 Bean） |

### 5.4 修改方案

**删除 `GlobalSafeFilter.java`，保留 `SqlInjectSafeInterceptor`，并移到 `config/security` 包下。**

```
重构前：
common/
├── GlobalSafeFilter.java          ← 删除
├── SqlInjectSafeInterceptor.java  ← 移到 config/security
├── GlobalExceptionHandler.java
├── Result.java
└── WebMvcConfig.java

重构后：
common/                            ← 只保留通用组件
├── GlobalExceptionHandler.java
├── Result.java
└── WebMvcConfig.java

config/security/                   ← 安全相关统一在此
├── SecurityConfig.java
├── JwtAuthenticationFilter.java
├── PasswordStrengthConfig.java
└── SqlInjectSafeInterceptor.java  ← 移入
```

同时删除 `DemoApplication.java` 上的 `@ServletComponentScan` 注解：

```java
// 重构前
@SpringBootApplication
@ServletComponentScan  // 扫描 @WebFilter，现在不需要了
@EnableAsync
public class DemoApplication { ... }

// 重构后
@SpringBootApplication
@EnableAsync
public class DemoApplication { ... }
```

### 5.5 学到什么？

**"不要重复自己"（DRY 原则：Don't Repeat Yourself）。**

实现同一功能，只保留一种方式。选择 Spring 拦截器的原因：
1. 更符合 Spring 生态（与 Spring MVC 深度集成）
2. 可以访问 Spring 容器中的 Bean（未来可能需要）
3. 配置更灵活（可以精确控制拦截路径）

## 六、Issue 4：缺少 DTO 层

### 6.1 问题现象

重构前，登录接口返回数据使用的是 `Map<String, Object>`：

```java
// AuthController.java
return Result.ok(Map.of(
    "token", token,
    "nickname", user.getNickname()
));
```

### 6.2 为什么这是问题？

1. **类型不安全**：`Map` 的 key 是字符串，写错了编译器不会报错
2. **没有文档**：看代码的人不知道返回了哪些字段
3. **难以扩展**：以后要加字段，需要翻代码找 `Map.of` 在哪里

### 6.3 企业级做法：DTO

DTO（Data Transfer Object）是专门用于 API 通信的对象：

```java
// 新建：dto/response/LoginResponse.java
public class LoginResponse {
    private String token;
    private String nickname;

    public LoginResponse() {}
    public LoginResponse(String token, String nickname) {
        this.token = token;
        this.nickname = nickname;
    }
    // getter / setter ...
}
```

**DTO 和 Entity 的区别：**

| 对比 | Entity（实体） | DTO（数据传输对象） |
|------|---------------|-------------------|
| 用途 | 对应数据库表 | 对应 API 接口 |
| 包含字段 | 所有数据库字段 | 只包含需要返回的字段 |
| 敏感信息 | 可能包含密码等 | 不包含敏感信息 |
| 变化原因 | 数据库结构变化 | 接口需求变化 |

### 6.4 修改后

```java
// AuthController.java
String token = jwtUtil.generateToken(username);
return Result.ok(new LoginResponse(token, user.getNickname()));
```

### 6.5 学到什么？

**DTO 层的核心价值：**

1. **解耦**：API 接口不直接暴露数据库结构
2. **安全**：可以控制哪些字段返回给前端
3. **清晰**：每个接口的请求/响应格式一目了然
4. **文档化**：DTO 本身就是接口文档

## 七、Issue 5：Controller 职责混杂

### 7.1 问题现象

重构前的 `UserController.java` 包含两类操作：

| 接口 | 操作者 | 权限 |
|------|--------|------|
| `DELETE /api/user/delete_admin` | 管理员 | 需要管理员权限 |
| `DELETE /api/user/delete_user` | 普通用户 | 登录即可（删自己） |
| `PUT /api/user/recover_admin` | 管理员 | 需要管理员权限 |
| `PUT /api/user/recover_user` | 普通用户 | 登录即可（恢复自己） |

### 7.2 为什么这是问题？

1. **职责不单一**：一个类同时处理管理员和普通用户的逻辑
2. **权限校验混乱**：有些方法校验角色，有些只校验登录
3. **难以维护**：代码量大，理解成本高
4. **不利于扩展**：以后加管理员功能或用户功能，都要改这个文件

### 7.3 修改方案

**拆分为两个 Controller：**

```
UserController.java（重构前）                  AdminUserController.java（新增）
├── 管理员删除用户（delete_admin）        →      ├── deleteUserByAdmin()
├── 用户注销自己（delete_user）            →      留在 UserController
├── 管理员恢复用户（recover_admin）        →      ├── recoverUserByAdmin()
└── 用户恢复自己（recover_user）            →      留在 UserController
```

**同时修复了一个隐藏 Bug：**

重构前，`recover_admin` 接口的权限校验是硬编码：

```java
// 重构前：硬编码校验
if(!"admin".equals(loginUsername)) {
    return Result.error(403, "权限不足，仅管理员可删除用户");
}
```

这段代码只会检查用户名是不是 `"admin"`，而不是检查角色。如果管理员改名叫 `superadmin`，这个接口就废了。

重构后改为角色校验：

```java
// 重构后：角色校验
if (!userService.isAdmin(loginUsername)) {
    return Result.error(403, "权限不足，仅管理员可恢复用户");
}
```

### 7.4 学到什么？

**Controller 设计原则：**

```
一个 Controller 只负责一类"角色"的操作

AdminUserController  → 管理员操作用户
UserController      → 用户操作自己
AuthController       → 认证相关（登录、注册、发验证码）
```

**为什么 Controller 要按角色拆分？**

1. **权限模型清晰**：管理员 Controller 全部需要管理员权限，用户 Controller 全部需要登录权限
2. **代码量适中**：每个文件 50-100 行，不会膨胀到几百行
3. **便于 Code Review**：管理员接口的改动只影响 AdminUserController

## 九、总结：企业级代码的几条原则

### 9.1 命名规范

```
Java 字段：驼峰命名（userRole, createTime）
数据库列：蛇形命名（user_role, create_time）
映射桥梁：@TableField("数据库列名")
```

### 9.2 分层清晰

```
Controller（接收请求、返回结果）
    ↓ 调用
Service（业务逻辑）
    ↓ 调用
Mapper（数据访问）
```

**每个 Service 只注入自己对应的 Mapper，不要交叉注入。**

### 9.3 职责单一

```
一个类只做一件事：
├── AdminUserController → 管理员操作
├── UserController → 用户自操作
├── AuthController → 认证功能
└── ...

一个方法只做一件事：
├── findByCode() → 按编码查询
├── findAllActive() → 查询所有可用
└── ...
```

### 9.4 消除重复

```
同一功能，只保留一种实现方式：
├── SQL 注入防护 → 保留 Spring 拦截器，删除 Servlet 过滤器
├── 权限校验 → 统一用 isAdmin() 方法，不用硬编码 "admin"
└── ...
```

### 9.5 使用 DTO

```
API 通信永远用 DTO，不用 Entity 或 Map：
├── Entity → 对应数据库，包含所有字段（含敏感信息）
├── DTO → 对应 API，只包含需要返回的字段
└── Map → 类型不安全，不要用
```

> 重构不是一次性的工作，而是一种持续的习惯。
> 每次看到"能跑但不太对"的代码，想一想：如果下个月有人来看这段代码，他能看懂吗？
> 保持这种意识，你的代码质量会越来越高。
