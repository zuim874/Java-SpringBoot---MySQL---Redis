# 分布式锁实践：从并发重复提交到数据一致

> 本文档记录为「修改密码」接口引入 Redis 分布式锁（Redisson）的完整过程。
> 背景：同一个用户**并发**提交多个修改密码请求时，可能出现"旧密码校验通过、但更新时密码已被改"的竞态问题。
> 目标：保证同一时刻只有一个修改密码请求在执行，并解决锁的正确释放问题。

## 一、为什么修改密码需要分布式锁？

### 1.1 并发场景还原

用户同时打开两个浏览器标签页，快速点击两次"修改密码"：

```
请求 A（旧密码校验通过）──── 开始更新密码 ──── 完成
请求 B（旧密码校验通过）──── 等待 ──── 更新密码（此时密码已被 A 改过！）
```

如果没有锁：

```
时间线：
T1  请求 A：校验旧密码 ✅（此时数据库密码还是旧密码）
T2  请求 B：校验旧密码 ✅（同样通过，因为 A 还没更新）
T3  请求 A：更新密码为 新密码A ✅
T4  请求 B：更新密码为 新密码B ✅（覆盖了 A 的结果）

结果：A 以为自己改成功了，但最终生效的是 B 的密码
```

**这就是经典的"并发竞态"（Race Condition）——检查与更新之间不是原子的。**

### 1.2 为什么不能用"先查再改"的简单方式

有人会说："我在更新前重新校验一次旧密码不就行了？"

```java
// 锁外校验旧密码（有竞态）
if (!passwordEncoder.matches(oldPassword, currentUser.getPassword())) {
    return error("原密码错误");
}
userService.updatePassword(id, newPassword);
```

这段代码在**单线程**下没问题，但在并发下：
- 两个请求可能**同时**通过旧密码校验
- 然后**同时**执行更新，后写的覆盖先写的

**所以需要一把"互斥锁"：让"校验旧密码 + 更新新密码"成为一个不可分割的临界区。**

## 二、本地锁、分布式锁、接口限流有什么区别？

| 方案 | 作用范围 | 能否解决并发竞态 | 典型场景 |
|------|----------|------------------|----------|
| `synchronized` / `ReentrantLock`（本地锁） | **单台 JVM** 内 | 多实例部署时**失效** | 单机应用 |
| Redis 分布式锁（Redisson） | **跨 JVM**（多实例共享） | ✅ 能 | 集群部署、接口幂等 |
| `@RateLimit`（接口限流） | 限制**调用频率** | ❌ 不能（只限频，不互斥） | 防刷、防恶意请求 |

```
并发控制的三个层次：

① 限流（RateLimit）→ 防止"短时间大量请求"→ 限频，不保证数据一致
② 本地锁           → 防止"同一 JVM 内并发"→ 多实例部署失效
③ 分布式锁         → 防止"多实例并发"→ 全局互斥，保证数据一致
```

**本项目是多实例部署（Spring Boot + 多台服务器 / 网关转发），所以需要分布式锁。**

## 三、Redisson 分布式锁核心概念

项目已集成 Redisson（`redisson-spring-boot-starter`），`RedisConfig` 中已配置 `RedissonClient`，并封装了 `RedisLockHelper` 工具类。

### 3.1 四个关键方法

```java
// ① 尝试加锁（看门狗版）：最多等待 waitTime 秒拿锁，拿到后由看门狗自动续期
boolean tryLock(String key, long waitTime, TimeUnit unit);

// ② 尝试加锁（指定租约版）：最多等待 waitTime 秒拿锁，拿到后最多持有 leaseTime 秒，到期强制过期
boolean tryLock(String key, long waitTime, long leaseTime, TimeUnit unit);

// ③ 释放锁：按 key 释放，内部判断"当前线程是否持有"，不会误删别人的锁
void unlock(String key);

// ④ 查询锁状态
boolean isLocked(String key);
```

### 3.2 两个容易误解的概念

**watchdog（看门狗）机制**：

```
lock.lock()            → 不指定 leaseTime → 开启看门狗，默认 30 秒自动续期
lock.tryLock(w, u)     → 不带 leaseTime → 开启看门狗，自动续期（本项目使用 ✅）
lock.tryLock(w, l, u)  → 指定了 leaseTime → 关闭看门狗，锁在 leaseTime 后强制过期
```

本项目使用看门狗版 `tryLock(key, 3, SECONDS)`：**最多等待 3 秒，拿到后由看门狗自动续期**（默认 30 秒、每 10 秒续期一次）。业务执行多久锁就持有多久，`unlock` 后停止续期；即使业务异常忘记释放锁，30 秒后锁也会自动过期兜底，不会造成永久死锁。

**为什么不用固定 leaseTime？**
固定租约（如 10 秒）存在隐患：若业务执行超过 10 秒，锁会被**提前自动释放**，下一个请求趁机进入临界区，互斥失效（并发竞态回归）。看门狗把锁的生命周期交给"业务是否结束"，从根上消除了这个风险。

**锁粒度**：

```
锁 key：user:change_password:lock:{userId}
          └─ 按用户 ID 区分 → 不同用户互不干扰，同一用户互斥
```

**锁粒度越细，并发度越高。** 用 `userId` 而不是全局 key，这样"用户 A 改密码"不会阻塞"用户 B 改密码"。

## 四、代码实现详解

修改后的 `UserController.changePassword` 核心结构：

```java
// 5. 分布式锁（看门狗模式）：同一用户同一时刻只允许一个改密码请求
String lockKey = "user:change_password:lock:" + currentUser.getId();
boolean locked = false;
try {
    // 尝试获取锁：最多等待 3 秒；拿到后由 Redisson 看门狗自动续期，
    // 业务执行多久锁就持有多久，不会因租约到期被提前释放（unlock 后停止续期）
    locked = redisLockHelper.tryLock(lockKey, 3, TimeUnit.SECONDS);
    if (!locked) {
        return Result.error(429, "操作正在处理，请勿重复提交");
    }

    // 6. 锁内双重检查（防止等待锁期间数据被其他请求修改）
    // 6.1 重新解析用户名
    String lockedUsername = jwtUtil.parseUsername(realToken);
    // 6.2 重新查询用户，确保拿到最新数据
    User lockedUser = userService.findUsernameforlogin(lockedUsername);
    // 6.3 重新校验旧密码
    if (!passwordEncoder.matches(oldPassword, lockedUser.getPassword())) {
        return Result.error(400, "原密码错误");
    }

    // 7. 更新密码
    boolean updated = userService.updatePassword(lockedUser.getId(),
            passwordEncoder.encode(newPassword));
    if (updated) {
        return Result.ok("密码修改成功");
    }
    return Result.error(500, "密码修改失败");
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // 恢复中断状态
    return Result.error(500, "系统繁忙，请稍后再试");
} catch (Exception e) {
    e.printStackTrace();
    return Result.error(500, "密码修改失败，请稍后重试");
} finally {
    // 8. 释放分布式锁（unlock 会停止看门狗续期；helper 内部判断当前线程是否持有，不会误释放他人锁）
    if (locked) {
        redisLockHelper.unlock(lockKey);
    }
}
```

### 4.1 为什么要有"锁内双重检查"？

```
场景：
请求 A 获取锁成功，正在处理（慢操作）
请求 B 等待锁（最多等 3 秒）

如果 A 在处理期间，其他线程修改了用户密码（比如通过另一个接口），
B 拿到锁时，B 一开始校验的 currentUser 是旧数据！

所以拿到锁后要"重新查库"：
  重新查用户 → 重新校验旧密码 → 再更新
这就是"双重检查"（Double Check）：锁外查一次 + 锁内再查一次。
```

### 4.2 为什么 `finally` 里必须释放锁？

```
如果不释放锁：
第 1 次请求  → 拿到锁 → 更新密码 → return（但没释放！）
第 2 次请求  → tryLock 等待 3 秒 → 拿不到 → 429
第 3、4、5...次请求 → 全部 429

看门狗模式下更要警惕：只要业务线程还持有锁，看门狗就会每 10 秒续期一次（每次续满 30 秒），
锁理论上可以一直不释放——"一直 429"会持续到业务线程结束或应用重启，远比固定租约（10 秒自愈）严重。

`finally` 里 `unlock` 是必须的：它既释放锁，又让看门狗停止续期；
若业务线程异常终止（或应用关闭），看门狗停止续期，30 秒后锁自动过期兜底，不会永久死锁。
```

`finally` 保证：**无论正常返回还是抛出异常，锁都会释放。**

```
finally + if(locked) 的双保险：
- 拿到锁（locked=true）→ 无论成功/失败都释放 ✅
- 没拿到锁（locked=false）→ 不释放（避免误删持有者的锁）✅
```

### 4.3 为什么 `InterruptedException` 要单独处理？

`tryLock` 声明抛出 `InterruptedException`（受检异常）。正确处理方式是：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();  // 恢复中断状态！
    return Result.error(500, "系统繁忙，请稍后再试");
}
```

**不要吞掉中断信号**：如果线程被中断（如应用关闭），`Thread.currentThread().interrupt()` 会把中断状态传回去，让上层知道这个线程不该继续跑。

## 五、踩坑记录：这次修复解决了什么

本次修改前，分布式锁的代码**不完整**，存在三个问题：

### 5.1 问题 1：try 没有 catch/finally（无法编译）

```java
// 修改前（不完整）
try {
    boolean locked = redisLockHelper.tryLock(...);
    if (!locked) { ... }
    try {
        // 双重检查 + 更新
    }
    // ❌ 内层 try 没有 catch/finally
}
// ❌ 外层 try 没有 catch/finally，Java 语法不允许
```

Java 语法规定 `try` 之后必须有 `catch` 或 `finally`，所以这段代码**根本编译不过**。

### 5.2 问题 2：锁永远不会释放

```java
// 修改前：拿到锁后 return，锁没人释放
boolean locked = redisLockHelper.tryLock(...);
if (!locked) { return 429; }

boolean updated = userService.updatePassword(...);
if (updated) {
    return Result.ok("密码修改成功");   // ❌ 直接 return，锁未释放
}
```

**后果**：第一个请求成功后锁一直存在，后续请求全部 429，直到 30 秒后锁自动过期（看门狗兜底）才恢复。表现就是"改一次密码后，短时间内再改就被拦截"。

### 5.3 问题 3：双重检查里解析 token 用错了变量

```java
// 修改前（bug）
loginUsername = jwtUtil.parseUsername(token.substring(7));
//                                        ^^^^^ token 带 "Bearer " 前缀！
```

方法开头已经用 `realToken = token.substring(7)` 剥离过前缀，锁内却用回原始 `token` 再剥一次——逻辑上等价，但容易混淆且多一次剥离。统一改用 `realToken` 更清晰。

### 5.4 修复后的完整流程

```
请求进入
  ├─ ① 校验 token（登录态）
  ├─ ② 查当前用户（锁外第一次检查）
  ├─ ③ 校验旧密码（锁外）
  ├─ ④ 密码强度校验
  ├─ ⑤ 尝试加锁（看门狗版，最多等 3 秒）→ 失败返回 429
  ├─ ⑥ 锁内双重检查（重新查用户 + 重新校验旧密码）
  ├─ ⑦ updateById 更新密码 + 清理缓存
  └─ finally 释放锁
```

## 六、总结与原则

### 6.1 本次学到的核心原则

```
1. 检查与更新必须原子
   "先校验后写入"在并发下不可靠，必须用锁把临界区包起来。

2. 锁必须带"兜底过期"
   看门狗模式靠默认 30 秒兜底；若关闭看门狗（指定 leaseTime），必须显式设置合理租约，
   防止代码异常导致死锁。

3. 释放锁必须放 finally
   正常返回、异常抛出都要释放，否则锁泄漏。

4. 锁粒度要细
   用 userId 做锁 key，不同用户互不阻塞，提高并发度。

5. 锁内要"双重检查"
   等待锁期间数据可能已变，拿到锁后重新查库再校验。

6. 区分限流与锁
   限流防"量"（频率），锁防"冲突"（互斥），两者配合使用。

7. 业务时长不确定时优先看门狗
   固定 leaseTime 存在"锁被提前释放、并发趁虚而入"的风险；
   看门狗让锁的生命周期跟随业务（unlock 才释放），从根上消除该风险。
```

### 6.2 代码模板：分布式锁的标准写法

```java
String lockKey = "业务:操作:lock:" + 资源ID;
boolean locked = false;
try {
    locked = redisLockHelper.tryLock(lockKey, 3, TimeUnit.SECONDS);  // 看门狗版：等待 3 秒，拿锁后自动续期
    if (!locked) {
        return Result.error(429, "操作正在处理，请勿重复提交");
    }
    // 锁内：双重检查 + 业务操作
    ...
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return Result.error(500, "系统繁忙，请稍后再试");
} catch (Exception e) {
    e.printStackTrace();
    return Result.error(500, "操作失败，请稍后重试");
} finally {
    if (locked) {
        redisLockHelper.unlock(lockKey);
    }
}
```

### 6.3 一句话总结

> **分布式锁不是"加锁"这一个动作，而是"tryLock + 业务 + finally 释放"的完整闭环。**
> 少一个 `finally`，锁就泄漏；不用看门狗又不设租约，异常就死锁；少一个"双重检查"，并发就钻空子。
