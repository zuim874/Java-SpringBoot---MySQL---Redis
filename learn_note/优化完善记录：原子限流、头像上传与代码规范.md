## 二、并发原子操作完善

### 2.1 限流计数不是原子的（INCR + EXPIRE）

#### 问题现象

`RateLimitAspect`（限流切面）原来的实现：

```java
// 修改前：两步操作
Long count = redisUtil.increment(redisKey, 1);   // 第1步：自增

if (count == 1) {
    redisUtil.expire(redisKey, window, SECONDS);  // 第2步：设置过期时间
}

if (count > rateLimit.maxRequests()) {
    return Result.error(429, rateLimit.message());  // 限流
}
```

#### 为什么这是问题？

```
increment（自增）和 expire（设置过期）是两个独立的 Redis 命令

并发场景：
T1: 线程A 执行 INCR → count = 1
T2: 线程B 执行 INCR → count = 2
T3: 线程A 执行 EXPIRE → 设置 60 秒过期 ✅
T4: 线程C 执行 INCR → count = 3

但如果 EXPIRE 失败（网络抖动、Redis 连接异常）：
    key 永远不会过期 → 这个 IP + 接口被"永久限流"！
```

**后果：** 一个用户可能被永久拦截，只有手动删 Redis key 才能恢复。

#### 解决方案：Lua 脚本把两步合并成一步

Redis 的 Lua 脚本在服务端**原子执行**，脚本执行期间不会有其他命令插入：

```java
// RedisUtil.java 新增
private static final DefaultRedisScript<Long> INCR_EXPIRE_SCRIPT = new DefaultRedisScript<>(
        "local c = redis.call('incr', KEYS[1]) " +
                "if c == 1 then " +
                "    redis.call('expire', KEYS[1], tonumber(ARGV[1])) " +
                "end " +
                "return c",
        Long.class
);

// 对外暴露原子方法
public Long incrementAndExpire(String key, long timeout, TimeUnit unit) {
    long seconds = unit.toSeconds(timeout);
    return redisTemplate.execute(
            INCR_EXPIRE_SCRIPT,
            Collections.singletonList(key),
            seconds
    );
}
```

```java
// RateLimitAspect.java 修改后：一次原子调用
Long count = redisUtil.incrementAndExpire(redisKey, rateLimit.window(), TimeUnit.SECONDS);

// Redis 异常时 count 为 null，降级放行（限流是"保护"不是"阻断"）
if (count != null && count > rateLimit.maxRequests()) {
    return Result.error(429, rateLimit.message());
}
```

#### 顺带修复的两个细节

1. **降级放行**：Redis 异常时 `count == null`，选择放行而不是拦截——保证业务可用性。
2. **Key 稳定性**：原来用 `joinPoint.getTarget().getClass().getName()` 拿类名，AOP 代理类的名字可能带 `$$`，改为 `joinPoint.getSignature().getDeclaringTypeName()` 拿接口声明的类型名，key 不会漂移。

**知识点：为什么 Lua 脚本是原子的？**

```
Redis 是单线程执行命令的。
Lua 脚本被当作"一个命令"提交给 Redis，
从脚本第一行到最后一行，中间不会有其他客户端命令插入。
所以"自增 + 设过期"在脚本内天然原子。
```

### 2.2 sendDeleteCode 限流判断写反了

#### 问题现象

`UserController.sendDeleteCode()`（发送注销验证码）里：

```java
// 修改前：逻辑反了！
Boolean success = redisUtil.setIfAbsent(sendLimitKey, "1", 60, TimeUnit.SECONDS);
if (!Boolean.FALSE.equals(success)) {   // ❌
    long ttl = redisUtil.getExpire(sendLimitKey, TimeUnit.SECONDS);
    return Result.error(400, "请等待 " + ttl + " 秒后再试");
}
```

#### 为什么这是问题？

`setIfAbsent` 的返回语义：

| 返回值 | 含义 | 应该做什么 |
|--------|------|-----------|
| `true` | key 不存在，**首次请求**设置成功 | ✅ 放行（发送验证码） |
| `false` | key 已存在，**60 秒内重复请求** | ❌ 拦截 |

而 `!Boolean.FALSE.equals(success)` 的判断结果：

| success | `Boolean.FALSE.equals(success)` | `!` 取反 | 行为 |
|---------|-------------------------------|---------|------|
| `true`（首次） | `false` | `true` | ❌ 被拦截！ |
| `false`（重复） | `true` | `false` | ✅ 放行！ |

**完全反了：首次请求被拦截，重复请求反而放行，限流形同虚设。**

#### 解决方案

```java
// 修改后：判断改为"是否等于 false"
Boolean firstRequest = redisUtil.setIfAbsent(sendLimitKey, "1", 60, TimeUnit.SECONDS);
if (Boolean.FALSE.equals(firstRequest)) {   // ✅ 只有重复请求才拦截
    long ttl = redisUtil.getExpire(sendLimitKey, TimeUnit.SECONDS);
    return Result.error(400, "请等待 " + ttl + " 秒后再试");
}
```

**踩坑提示：** 布尔判断的取反很容易写错。建议统一用 `Boolean.FALSE.equals(x)` 这种"显式等于"的写法，不要用 `!xxx.equals()`，可读性更好、更不容易错。

### 2.3 三个发送验证码接口限流模式不统一

#### 问题现象

项目里有三个"发送验证码"接口，原来用了两种不同的写法：

| 接口 | 方法 | 写法 |
|------|------|------|
| 注册验证码 | `AuthController.sendVerificationCode` | `hasKey` 检查 + 最后 `set` |
| 注销验证码 | `UserController.sendDeleteCode` | `setIfAbsent`（且逻辑写反） |
| 恢复验证码 | `UserController.sendRecoverCode` | `setIfAbsent`（正确） |

#### 为什么这是问题？

- 三种写法维护成本高，改一处容易漏掉其他两处
- `hasKey + set` 不是原子的：两个并发请求可能同时通过 `hasKey` 检查，都发验证码（上篇文档《并发问题与原子操作》已详细讲过）

#### 解决方案：统一为一种模式

```
统一顺序：
① 业务校验（邮箱格式、是否已注册）   ← 前置，避免无效请求占用限流窗口
② setIfAbsent 原子防刷              ← 一次原子操作
③ 生成验证码 → 存 Redis → 发邮件
```

```java
// 统一的骨架（以注册验证码为例）
if (userService.isEmailExist(email)) {
    return Result.error(400, "该邮箱已被注册");      // ① 业务校验在前
}

String sendLimitKey = "verify_registerCode_limit:" + email;
Boolean firstRequest = redisUtil.setIfAbsent(sendLimitKey, "1", 60, TimeUnit.SECONDS);
if (Boolean.FALSE.equals(firstRequest)) {             // ② 原子防刷
    long ttl = redisUtil.getExpire(sendLimitKey, TimeUnit.SECONDS);
    return Result.error(400, "请等待 " + ttl + " 秒后再试");
}

String code = generateVerificationCode.generateVerificationCode();
redisUtil.set(redisKey, code, 5, TimeUnit.MINUTES);   // ③ 存码发信
emailUtil.sendXXX(email, code);
```

**为什么业务校验要放在限流之前？**

如果限流 key 在方法开头就写入，而业务校验失败（如邮箱已注册）提前返回，限流 key 仍然存在 60 秒——用户修好后重试，反而被"请等待"拦截，体验极差（这也是之前"发送邮件一直被限流拦截"问题的根因之一）。

### 2.4 save 方法：插入失败也写缓存

#### 问题现象

```java
// 修改前
public boolean save(User user) {
    boolean result = userMapper.insert(user) > 0;
    redisUtil.set(cacheKey, user, 10, TimeUnit.MINUTES);  // ❌ 无条件写缓存
    return result;
}
```

#### 为什么这是问题？

如果 `insert` 失败（比如唯一索引冲突），`result = false`，但缓存仍然写入了这个用户对象。下次查询直接从缓存命中一个**数据库里不存在**的用户。

#### 解决方案

```java
// 修改后：插入成功才写缓存
boolean result = userMapper.insert(user) > 0;
if (result) {
    redisUtil.set(cacheKey, user, 10, TimeUnit.MINUTES);
}
return result;
```

**知识点：缓存写入要"跟着数据库的成功走"。** 数据库写失败了，缓存就不该有这条数据，否则缓存就成了"假数据的源头"。

## 三、头像上传功能（前后端）

> 原项目 `User` 实体有 `avatar` 字段，但没有任何上传接口和前端 UI，属于"字段预留、功能缺失"。

### 3.1 后端：文件存储服务

新建 `Service/FileStorageService.java`，职责单一——**只负责文件的保存与 URL 生成**：

```java
@Service
public class FileStorageService {
    private static final List<String> ALLOWED_IMAGE_EXT = List.of("jpg", "jpeg", "png", "gif", "webp");
    private static final long MAX_AVATAR_SIZE = 2 * 1024 * 1024;  // 2MB

    public String storeAvatar(MultipartFile file) {
        // 1. 非空校验
        if (file == null || file.isEmpty()) {
            throw new IllegalArgumentException("上传文件不能为空");
        }
        // 2. 大小校验
        if (file.getSize() > MAX_AVATAR_SIZE) {
            throw new IllegalArgumentException("头像文件大小不能超过 2MB");
        }
        // 3. 扩展名白名单（防止上传 .exe 等非图片）
        String ext = ...;
        if (!ALLOWED_IMAGE_EXT.contains(ext)) {
            throw new IllegalArgumentException("仅支持 jpg/jpeg/png/gif/webp 格式的图片");
        }
        // 4. UUID 文件名（避免用户文件名注入 / 覆盖已有文件）
        String filename = UUID.randomUUID().toString().replace("-", "") + "." + ext;
        // 5. 落盘
        file.transferTo(new File(avatarDir, filename));
        // 6. 返回浏览器可访问的 URL
        return "/uploads/avatars/" + filename;
    }
}
```

**安全设计要点：**

| 防护点 | 措施 |
|--------|------|
| 文件类型 | 扩展名白名单（只允许图片） |
| 文件大小 | 2MB 上限（前后端双重限制） |
| 文件名 | 服务端重新生成 UUID，忽略用户上传的文件名（防路径穿越 `../`） |
| 存储目录 | 固定在项目 `uploads/avatars/` 下 |

### 3.2 后端：两个新接口

**接口 1：`GET /api/user/me` —— 获取当前登录用户信息**

头像上传的前提是前端要知道当前用户是谁、有没有头像，所以先补一个"获取我的信息"接口：

```java
@GetMapping("/me")
```

**为什么返回前要清空 password？**

之前 `User` 实体上可以加 `@JsonIgnore`，但项目重构后实体上没有这个注解了。在接口层显式 `setPassword(null)` 是"服务端兜底脱敏"，保证敏感字段绝不通过 HTTP 泄露。

**接口 2：`POST /api/user/avatar` —— 上传/更新头像**

```java
@RateLimit(window = 60, maxRequests = 5, message = "头像上传过于频繁，请稍后再试")
@PostMapping("/avatar")
public Result<?> uploadAvatar(@RequestHeader("Authorization") String token,
                              @RequestParam("file") MultipartFile file) {
    // 1. 校验 token
    // 2. 查当前用户
    // 3. 保存文件（FileStorageService 内完成类型/大小校验）
    String avatarUrl;
    try {
        avatarUrl = fileStorageService.storeAvatar(file);
    } catch (IllegalArgumentException e) {
        return Result.error(400, e.getMessage());   // 校验失败 → 400
    }
    // 4. 更新数据库 + 清理 Redis 缓存
    boolean updated = userService.updateAvatar(currentUser.getId(), avatarUrl);
    return Result.ok(avatarUrl);   // 返回新头像 URL 给前端
}
```

**`UserService.updateAvatar` 的缓存处理：**

```java
public boolean updateAvatar(Long id, String avatarUrl) {
    // 1. 更新数据库
    boolean result = userMapper.updateById(update) > 0;
    if (result) {
        // 2. 删除该用户所有维度的缓存
        //    demo:user:login:active:{username}
        //    demo:user:login:all:{username}
        //    demo:user:id:{id}
        // 下次查询会重新从数据库加载，拿到最新头像
    }
    return result;
}
```

**知识点：更新了数据库，缓存怎么办？**

标准做法是**"更新数据库 + 删除缓存"**（Cache-Aside 的写路径），让下次查询重新加载，而不是"更新数据库 + 更新缓存"——因为更新缓存需要构造完整对象，容易漏字段，删缓存更简单可靠。

### 3.4 前端：request.js 的坑

#### 问题现象

```javascript
// 修改前
const mergedOptions = { ...defaultOptions, ...options }
```

#### 为什么这是问题？

如果调用方传了自定义 `headers`（比如文件上传时），`...options` 会**整体覆盖** `defaultOptions.headers`，导致 `Authorization`（token）丢失！

```
defaultOptions.headers = { 'Content-Type': 'application/json', 'Authorization': 'Bearer xxx' }
options.headers       = { 'Content-Type': 'multipart/form-data' }

合并结果：headers 变成了 { 'Content-Type': 'multipart/form-data' }
                 ← Authorization 丢了！后端返回 401
```

#### 解决方案

```javascript
// 修改后：headers 单独逐层合并
const headers = { ...defaultOptions.headers, ...(options.headers || {}) }

// 文件上传：删除 Content-Type，让浏览器自动生成 multipart boundary
if (options.body instanceof FormData) {
    delete headers['Content-Type']
}
// 普通表单：改为 x-www-form-urlencoded
else if (options.body instanceof URLSearchParams) {
    headers['Content-Type'] = 'application/x-www-form-urlencoded'
}

const mergedOptions = { ...defaultOptions, ...options, headers }
```

**知识点：对象展开合并（spread）是浅合并。** 嵌套对象（如 headers）会被整体替换而不是逐字段合并，要合并嵌套结构必须手动处理。

## 四、代码规范修复

### 4.1 密码被 sanitize 篡改（安全隐患）

#### 问题现象

登录/注册时，密码也走了 `sanitizeUtil.sanitize()`：

```java
// 修改前
password = sanitizeUtil.sanitize(password);
```

`sanitize` 会把单引号 `'` 删掉、把 `<` 替换成 `&lt;`、把 `--` 删掉……

```
用户设置的密码：abc'123
实际存入的密码：abc123        ← 单引号被删了！

用户以为密码是 abc'123，永远无法登录（输入 abc'123 和存库的 abc123 不匹配）
```

#### 为什么这是问题？

1. **篡改用户数据**：密码是"语义敏感"数据，用户设置什么就应该存什么
2. **注入防护的误解**：密码用 BCrypt 加密后存储，本身就不含可注入 SQL/HTML 的明文；`sanitize` 防护的是会拼进 SQL/HTML 的**展示性文本**（用户名、昵称、邮箱），不是密码

#### 解决方案

```java
// 修改后：密码只 trim，不做字符替换
password = password.trim();
```

配套：给 `email` 增加格式校验（`EmailUtil.isValidEmail`），防止恶意格式的邮箱进入后续流程。

### 4.2 正则每次请求重复编译

#### 问题现象

```java
// 修改前：每次请求都重新编译正则
if (val != null && val.toLowerCase().matches(DANGER_REG)) {
```

#### 解决方案

```java
// 修改后：预编译 + 忽略大小写，一次编译多次使用
private static final Pattern DANGER_PATTERN =
        Pattern.compile(DANGER_REG, Pattern.CASE_INSENSITIVE);

if (val != null && DANGER_PATTERN.matcher(val).matches()) {
```

**知识点：`String.matches()` 内部每次都会 `Pattern.compile`。** 正则编译是有开销的（生成状态机），在高频路径上应该预编译为 `Pattern` 常量复用。

### 4.3 验证码用 Random 可预测

#### 问题现象

```java
// 修改前：Random 是伪随机数，可预测
Random random = new Random();
code.append(random.nextInt(10));
```

#### 为什么这是问题？

验证码是安全凭证。`java.util.Random` 基于固定种子算法，攻击者可以预测后续输出；如果验证码可预测，攻击者就能"猜"出验证码。

#### 解决方案

```java
// 修改后：SecureRandom 是加密安全随机数
private static final SecureRandom RANDOM = new SecureRandom();
code.append(RANDOM.nextInt(10));
```

**知识点：`Random` vs `SecureRandom`。**

| 对比 | Random | SecureRandom |
|------|--------|--------------|
| 用途 | 游戏、随机抽样 | 安全凭证（验证码、token、盐） |
| 可预测性 | 可预测（线性同余） | 不可预测（操作系统熵源） |
| 性能 | 快 | 略慢 |

**凡是和安全相关的随机数，一律用 `SecureRandom`。**

## 六、总结与心得

### 6.1 本次学到的核心原则

```
1. 原子性优先
   需要"检查+操作"的地方，优先用 Redis 原子命令 / Lua 脚本，
   不要用"两步走"（先查再写），两步之间一定有并发窗口。

2. 缓存跟着数据库的成功走
   数据库写失败 → 缓存不写；数据库更新 → 删除缓存让下次重载。

3. 安全看"边界"
   密码、token 等安全数据：不 sanitize、用 SecureRandom；
   文件上传：白名单 + 大小限制 + 服务端重命名（防路径穿越）。

4. 前后端校验各司其职
   后端校验是底线，前端校验是体验，缺一不可。

5. 统一优于分散
   三个类似的接口，用同一种模式写，维护成本最低。
```

### 6.2 几个值得记住的"坑"

| 坑 | 教训 |
|----|------|
| `!Boolean.FALSE.equals(x)` | 布尔取反容易写反，用 `Boolean.FALSE.equals(x)` 显式判断 |
| `{...a, ...b}` 浅合并 headers | 嵌套对象会被整体覆盖，要手动逐层合并 |
| `String.matches()` 每次编译正则 | 高频路径用预编译 `Pattern` |
| 限流 key 提前写入 | 业务校验失败也会占用限流窗口，校验要前置 |
| `Random` 用于验证码 | 安全相关随机数必须用 `SecureRandom` |

### 6.3 一句话总结

> **优化的本质不是"改得多"，而是"每处改动都有理由"——
> 要么修了隐患，要么补了缺失，要么让后来的维护者少踩一个坑。**
