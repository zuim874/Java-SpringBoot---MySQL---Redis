## 一、为什么需要消息队列？

### 1.1 一个直观的例子

假设用户点击"发送验证码"按钮：

```
用户点击 "发送验证码"
    ↓
Controller 接收请求
    ↓
生成 6 位验证码
    ↓
存入 Redis（5 分钟过期）
    ↓
调用邮件服务发送邮件  ← 这里要等 1-3 秒
    ↓
返回 "验证码已发送"

用户等待时间 = 生成验证码 + Redis 写入 + 邮件发送（1-3秒）
```

**问题：** 邮件发送需要 1-3 秒，用户必须等待这段时间才能看到"验证码已发送"的提示。

### 1.2 引入 MQ 后的流程

```
用户点击 "发送验证码"
    ↓
Controller 接收请求
    ↓
生成 6 位验证码
    ↓
存入 Redis（5 分钟过期）
    ↓
把"发送邮件"任务发送到消息队列  ← 这里只要几毫秒
    ↓
立即返回 "验证码已发送"

用户等待时间 = 生成验证码 + Redis 写入 + 消息入队（< 50ms）
```

后台的"消费者"会异步处理邮件发送，用户不需要等待。

### 1.3 MQ 的三大作用

```
┌─────────────────────────────────────────────────────┐
│                  消息队列的三大作用                     │
├─────────────────────────────────────────────────────┤
│  1. 异步解耦：发送方不需要等待接收方处理完成             │
│  2. 削峰填谷：瞬间高流量时，MQ 会缓冲请求，慢慢处理      │
│  3. 可靠通信：消息持久化，即使服务重启也不会丢失          │
└─────────────────────────────────────────────────────┘
```

## 三、技术选型：为什么选 ActiveMQ？

### 3.1 常见消息队列对比

| 特性 | ActiveMQ | Kafka | Redis Stream |
|------|----------|-------|-------------|
| 学习成本 | 低 | 高 | 低 |
| 消息可靠性 | 高（持久化 + 确认机制） | 高 | 中（依赖 Redis） |
| 吞吐量 | 万级/秒 | 百万级/秒 | 万级/秒 |
| 路由灵活度 | 高（Queue + Topic 两种模式） | 低（Topic 模式） | 低 |
| Spring Boot 支持 | 非常好（Spring JMS） | 一般 | 一般 |
| 运维复杂度 | 低（有 Web 管理界面） | 高 | 低（无需额外安装） |

**选择 ActiveMQ 的原因：**

```
本项目是中小型 Web 应用，特点是：
1. 消息量不大（每天几百封邮件）
2. 需要 Queue 和 Topic 两种模式
3. Spring Boot 集成最成熟（spring-boot-starter-activemq）
4. 运维简单（有 Web 管理界面，端口 8161）
5. 支持 JMS 标准，API 统一

→ ActiveMQ 是最合适的选择
```

### 3.2 备选方案：Redis Stream

如果不想额外安装 ActiveMQ，可以利用项目已有的 Redis 实现 Stream 消息队列：

```
优点：不需要额外安装中间件
缺点：功能不如 ActiveMQ 完善
适用：非常简单的异步任务
```

本文档以 ActiveMQ 为主，附录中也会给出 Redis Stream 的简化方案。

## 四、ActiveMQ 核心概念

### 4.1 两个核心目的地类型

```
┌──────────┐     ┌──────────────────┐     ┌──────────┐
│  Producer │────▶│  Destination     │────▶│ Consumer │
│ （生产者） │     │  （Queue / Topic） │     │ （消费者） │
└──────────┘     └──────────────────┘     └──────────┘
```

| 概念 | 说明 | 生活中的例子 |
|------|------|------------|
| **Producer** | 发送消息的程序 | 你寄快递 |
| **Queue** | 点对点模式，一条消息只被一个消费者消费 | 快递送到你家 |
| **Topic** | 发布/订阅模式，一条消息被所有订阅者消费 | 广播通知 |
| **Consumer** | 接收并处理消息的程序 | 收快递的人 |

### 4.2 Queue vs Topic 的区别

```
Queue（点对点）：
消息发送者 → Queue
    ↓
只有一个消费者能收到消息
    ↓
消息被消费后即删除
适用：任务分配（如邮件发送，只需要一个服务实例处理）

Topic（发布/订阅）：
消息发送者 → Topic
    ↓
    ↓         ↓
消费者1    消费者2    消费者3
    ↓         ↓         ↓
所有订阅者都能收到消息
适用：广播通知（如缓存刷新，所有服务实例都需要处理）
```

**本项目主要使用 Queue 模式，Topic 用于广播场景。**

### 4.3 消息的生命周期

```
生产者发送消息（JmsTemplate.convertAndSend）
    ↓
消息进入 ActiveMQ 的 Queue 或 Topic
    ↓
消息持久化到磁盘（持久化模式）
    ↓
ActiveMQ 推送给消费者（或消费者拉取）
    ↓
消费者处理消息
    ↓
消费者发送确认（ACK）
    ↓
ActiveMQ 删除消息
```

### 6.3 ActiveMQ 配置类

```java
package com.xuwenye.demo.config.activeMQ;

import org.apache.activemq.ActiveMQConnectionFactory;
import org.apache.activemq.command.ActiveMQQueue;
import org.apache.activemq.command.ActiveMQTopic;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.config.JmsListenerContainerFactory;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.jms.support.converter.MappingJackson2MessageConverter;
import org.springframework.jms.support.converter.MessageConverter;
import org.springframework.jms.support.converter.MessageType;

import jakarta.jms.Queue;
import jakarta.jms.Topic;

/**
 * ActiveMQ 消息队列配置类
 *
 * 作用：
 * 1. 定义 Queue 和 Topic 目的地
 * 2. 配置消息转换器（Java 对象 ↔ JSON）
 * 3. 配置 JmsTemplate（发送消息的模板类）
 * 4. 配置监听器容器工厂（Queue 和 Topic 两种模式）
 */
@Configuration
public class ActiveMQConfig {

    // ==================== Queue 名称常量 ====================
    public static final String QUEUE_EMAIL = "demo.email.queue";        // 邮件队列
    public static final String QUEUE_SMS = "demo.sms.queue";            // 短信队列
    public static final String QUEUE_LOG = "demo.log.queue";            // 日志队列
    public static final String QUEUE_ORDER = "demo.order.queue";        // 订单队列
    public static final String QUEUE_STATISTICS = "demo.statistics.queue"; // 统计队列
    public static final String QUEUE_FILE = "demo.file.queue";          // 文件处理队列
    public static final String QUEUE_NOTIFICATION = "demo.notification.queue"; // 通知队列

    // ==================== Topic 名称常量 ====================
    public static final String TOPIC_BROADCAST = "demo.broadcast.topic";    // 广播 Topic
    public static final String TOPIC_ALERT = "demo.alert.topic";            // 告警 Topic

    @Value("${spring.activemq.broker-url}")
    private String brokerUrl;

    @Value("${spring.activemq.user}")
    private String user;

    @Value("${spring.activemq.password}")
    private String password;

    // ==================== 1. 连接工厂 ====================

    /**
     * ActiveMQ 连接工厂
     *
     * 作用：创建与 ActiveMQ 服务器的连接
     * 配置了 Broker URL、用户名、密码
     */
    @Bean
    public ActiveMQConnectionFactory connectionFactory() {
        ActiveMQConnectionFactory factory = new ActiveMQConnectionFactory();
        factory.setBrokerURL(brokerUrl);
        factory.setUserName(user);
        factory.setPassword(password);
        // 开启信任所有包（支持传递序列化对象）
        factory.setTrustAllPackages(true);
        return factory;
    }

    // ==================== 2. 消息转换器 ====================

    /**
     * MappingJackson2MessageConverter
     *
     * 作用：把 Java 对象自动转为 JSON 存入消息队列
     * 消费者收到后自动反序列化为 Java 对象
     *
     * 如果不配置这个，默认使用 SimpleMessageConverter（只能传 String 和 byte[]）
     */
    @Bean
    public MessageConverter messageConverter() {
        MappingJackson2MessageConverter converter = new MappingJackson2MessageConverter();
        converter.setTargetType(MessageType.TEXT);
        converter.setTypeIdPropertyName("_type");
        return converter;
    }

    // ==================== 3. JmsTemplate ====================

    /**
     * JmsTemplate 是 Spring JMS 提供的"发送消息的模板类"
     *
     * 类似 RestTemplate（发 HTTP 请求）和 RedisTemplate（操作 Redis）
     * JmsTemplate 就是用来"发送消息到 ActiveMQ"的
     */
    @Bean
    public JmsTemplate jmsTemplate(ActiveMQConnectionFactory connectionFactory,
                                   MessageConverter messageConverter) {
        JmsTemplate template = new JmsTemplate(connectionFactory);
        template.setMessageConverter(messageConverter);
        // 启用发布/订阅模式（发送到 Topic）
        template.setPubSubDomain(false); // false = Queue 模式，true = Topic 模式
        // 发送超时
        template.setReceiveTimeout(3000);
        return template;
    }

    /**
     * 专门用于 Topic 的 JmsTemplate
     * pubSubDomain=true 表示发送到 Topic
     */
    @Bean
    public JmsTemplate topicJmsTemplate(ActiveMQConnectionFactory connectionFactory,
                                        MessageConverter messageConverter) {
        JmsTemplate template = new JmsTemplate(connectionFactory);
        template.setMessageConverter(messageConverter);
        template.setPubSubDomain(true); // Topic 模式
        template.setReceiveTimeout(3000);
        return template;
    }

    // ==================== 4. 监听器容器工厂 ====================

    /**
     * Queue 模式的监听器容器工厂
     *
     * 用于 @JmsListener 注解，监听 Queue 中的消息
     * 默认使用 CLIENT_ACKNOWLEDGE 手动确认模式
     */
    @Bean
    public JmsListenerContainerFactory<?> queueListenerContainerFactory(
            ActiveMQConnectionFactory connectionFactory) {
        DefaultJmsListenerContainerFactory factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setPubSubDomain(false); // Queue 模式
        factory.setSessionAcknowledgeMode(jakarta.jms.Session.CLIENT_ACKNOWLEDGE);
        return factory;
    }

    /**
     * Topic 模式的监听器容器工厂
     *
     * 用于 @JmsListener 注解，监听 Topic 中的消息
     * 设置 setPubSubDomain(true) 表示订阅 Topic
     */
    @Bean
    public JmsListenerContainerFactory<?> topicListenerContainerFactory(
            ActiveMQConnectionFactory connectionFactory) {
        DefaultJmsListenerContainerFactory factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setPubSubDomain(true); // Topic 模式
        factory.setSessionAcknowledgeMode(jakarta.jms.Session.CLIENT_ACKNOWLEDGE);
        return factory;
    }

    // ==================== 5. 定义 Queue 目的地 ====================

    @Bean
    public Queue emailQueue() { return new ActiveMQQueue(QUEUE_EMAIL); }

    @Bean
    public Queue logQueue() { return new ActiveMQQueue(QUEUE_LOG); }

    @Bean
    public Queue orderQueue() { return new ActiveMQQueue(QUEUE_ORDER); }

    @Bean
    public Queue smsQueue() { return new ActiveMQQueue(QUEUE_SMS); }

    @Bean
    public Queue statisticsQueue() { return new ActiveMQQueue(QUEUE_STATISTICS); }

    @Bean
    public Queue fileQueue() { return new ActiveMQQueue(QUEUE_FILE); }

    @Bean
    public Queue notificationQueue() { return new ActiveMQQueue(QUEUE_NOTIFICATION); }

    // ==================== 6. 定义 Topic 目的地 ====================

    @Bean
    public Topic broadcastTopic() { return new ActiveMQTopic(TOPIC_BROADCAST); }

    @Bean
    public Topic alertTopic() { return new ActiveMQTopic(TOPIC_ALERT); }
}
```

### 7.2 引入 MQ 后的代码

**第一步：定义消息体（DTO）**

```java
package com.xuwenye.demo.dto.mq;

/**
 * 邮件消息体
 *
 * 为什么需要 DTO？
 * 1. 消息在网络上传输，需要序列化（Java 对象 → JSON）
 * 2. DTO 明确规定了消息的格式，生产者和消费者之间约定清晰
 * 3. 后续修改消息格式时，只需要改 DTO，不需要改所有调用方

public class EmailMessage {

    /** 邮件类型：REGISTER（注册验证码）、RECOVER（恢复账号） */
    private String type;

    /** 收件人邮箱 */
    private String email;

    /** 验证码 */
    private String code;

    /** 发送时间 */
    private String timestamp;

    public EmailMessage() {}

    public EmailMessage(String type, String email, String code) {
        this.type = type;
        this.email = email;
        this.code = code;
        this.timestamp = java.time.LocalDateTime.now().toString();
    }

    // Getters & Setters（省略，实际代码需要）
    public String getType() { return type; }
    public void setType(String type) { this.type = type; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public String getCode() { return code; }
    public void setCode(String code) { this.code = code; }
    public String getTimestamp() { return timestamp; }
}
```

**MQProducer 实现：**

```java
package com.xuwenye.demo.Service;

import com.xuwenye.demo.config.activeMQ.ActiveMQConfig;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Component;

/**
 * 消息队列生产者
 *
 * 封装 JmsTemplate，提供统一的发送消息接口
 * 所有需要发送消息的地方都通过这个类
 */
@Component
public class MQProducer {

    private final JmsTemplate jmsTemplate;

    public MQProducer(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    /**
     * 发送邮件消息到邮件队列
     */
    public void sendEmail(Object message) {
        jmsTemplate.convertAndSend(ActiveMQConfig.QUEUE_EMAIL, message);
    }

    /**
     * 发送日志消息到日志队列
     */
    public void sendLog(Object message) {
        jmsTemplate.convertAndSend(ActiveMQConfig.QUEUE_LOG, message);
    }

    /**
     * 发送订单消息到订单队列
     */
    public void sendOrder(Object message) {
        jmsTemplate.convertAndSend(ActiveMQConfig.QUEUE_ORDER, message);
    }

    /**
     * 发送广播消息到广播 Topic
     * 所有订阅了该 Topic 的消费者都会收到
     */
    public void sendBroadcast(Object message) {
```

## 九、场景 3：缓存刷新与一致性

### 9.1 现状问题

```
当前缓存刷新方式：
写操作（更新用户信息）→ 删除 Redis 缓存 → 直接返回

问题：
1. 如果在集群部署（多台服务器），A 服务器删除了缓存
   B 服务器可能还在用旧缓存
2. 删除缓存的操作是"发了就忘"，没有确认机制
```

### 9.2 使用 Topic 广播缓存刷新

```
写操作（任何服务器）
    ↓
发送缓存刷新消息到 Topic（demo.broadcast.topic）
    ↓
所有服务器实例都收到消息
    ↓
每台服务器各自删除本地缓存
```

### 9.3 生产者：在 UserService 中发送缓存刷新消息

```java
// UserService.java 改造后
@Service
public class UserService {

    private final MQProducer mqProducer;  // 注入 MQ 生产者

    public UserService(MQProducer mqProducer, /* 其他依赖 */) {
        this.mqProducer = mqProducer;
    }

    // 删除用户后刷新缓存
    public boolean deleteById(Long id) {
        User user = userMapper.selectById(id);
        boolean result = userMapper.deleteById(id) > 0;

        if (result && user != null) {
            // 本地删除缓存
            redisTemplate.delete("demo:user:login:active:" + user.getUsername());
            redisTemplate.delete("demo:user:login:all:" + user.getUsername());

            // 广播通知其他服务实例也刷新缓存
            mqProducer.sendBroadcast("cache_refresh:user:" + user.getUsername());
        }
        return result;
    }
}
```

### 9.4 消费者：刷新缓存

```java
// MQConsumer.java 中新增缓存刷新消费者
@JmsListener(destination = ActiveMQConfig.TOPIC_BROADCAST,
             containerFactory = "topicListenerContainerFactory")
public void handleCacheRefresh(Message message) {
    try {
        if (message instanceof TextMessage) {
            String text = ((TextMessage) message).getText();
            // 消息格式：cache_refresh:user:admin
            // 提取出要刷新的缓存 key
            String cacheKey = text.replace("cache_refresh:", "");

            // 删除对应的缓存
            Set<String> keys = redisTemplate.keys("demo:user:login:*:" + cacheKey);
            if (keys != null && !keys.isEmpty()) {
                redisTemplate.delete(keys);
                System.out.println("缓存已刷新：" + keys);
            }

            message.acknowledge();
        }
    } catch (Exception e) {
        System.err.println("缓存刷新失败：" + e.getMessage());
    }
}
```

## 十一、MQ 的可靠性保障

### 11.1 消息丢失的场景

```
消息从发送到消费，经过三个环节：

生产者 → ActiveMQ → 消费者

每个环节都可能丢失消息：
1. 生产者发送时网络中断 → 消息没到 ActiveMQ
2. ActiveMQ 收到后宕机 → 消息丢失（如果没持久化）
3. 消费者收到后崩溃 → 消息丢失（如果自动确认）
```

### 11.2 解决方案：三层保障

```
第一层：生产者确认
    使用 JmsTemplate 发送消息，默认等待 Broker 确认
    如果发送失败，抛出异常，可以提供重试机制

第二层：消息持久化（默认开启）
    消息写入磁盘，ActiveMQ 重启后消息还在
    配置：默认使用持久化模式（PERSISTENT）

第三层：消费者手动确认（CLIENT_ACKNOWLEDGE）
    消费者处理完消息后才调用 message.acknowledge()
    如果处理失败，消息会重新投递
```

### 11.3 配置代码

```properties
# application.properties 中已配置
spring.jms.listener.acknowledge-mode=client     # 手动确认
```

### 11.4 消费失败的处理策略

```
消费者处理消息失败
    ↓
消息重新投递（Redelivery）
    ↓
ActiveMQ 默认重试 6 次
    ↓
还是失败
    ↓
┌──────────────────────────────────────────────┐
│            两种处理方式                         │
├──────────────────────────────────────────────┤
│  方式1：记录日志 + 放入死信队列                 │
│  适用：非关键消息（如审计日志）                   │
│                                              │
│  方式2：自定义重试策略                          │
│  适用：关键消息（如订单、支付）                   │
│  配置 redeliveryPlugin 限制重试次数             │
└──────────────────────────────────────────────┘
```

## 十三、总结与心得

### 13.1 引入 MQ 后的架构变化

```
引入 MQ 前：
Controller → Service → EmailUtil（同步）
                 ↓
            Redis / MySQL

引入 MQ 后：
Controller → Service → MQProducer → ActiveMQ 队列（异步，几毫秒）
                 ↓
            Redis / MySQL
                 ↓
           MQConsumer（后台处理）
```

### 13.2 核心价值

```
1. 用户体验提升
   验证码发送从等待 1-3 秒 → 瞬间返回

2. 系统解耦
   邮件服务挂了不影响注册流程
   邮件服务恢复后自动处理积压消息

3. 可扩展性
   新增功能只需要加新的消费者
   不需要修改现有代码

4. 削峰填谷
   瞬间大量注册请求时，MQ 缓冲消息
   消费者按自己的节奏处理，不会压垮邮件服务器
```

### 13.3 注意事项

```
1. 不要滥用 MQ
   简单操作（如密码加密）不需要 MQ
   只有耗时操作（邮件、日志）才适合

2. 消息幂等性
   消费者可能处理同一条消息多次
   确保重复处理不会产生副作用

3. 监控告警
   关注 ActiveMQ 管理界面中的队列积压情况
   消息堆积过多说明消费者处理不过来

4. 消息大小
   不要发送大消息（如 > 10MB）
   大消息用文件存储，MQ 只传文件路径

5. 事务管理
   消息发送和业务操作应该在同一个事务中
   业务回滚时，消息不应该被发送
```

### 13.4 面试常见问题

**Q1：为什么用 ActiveMQ 而不是 Kafka？**

> 本项目是中小型 Web 应用，每天消息量在几百到几千条级别。
> ActiveMQ 的吞吐量完全够用，而且 Spring Boot 集成最成熟，
> 运维简单（有 Web 管理界面，端口 8161）。
> Kafka 适合每天几百万条消息的大数据场景，对这个项目来说太重了。

**Q2：MQ 消息丢失了怎么办？**

> 三层保障：生产者确认（JmsTemplate 默认等待确认）、消息持久化（默认开启）、
> 消费者手动确认（CLIENT_ACKNOWLEDGE）。三个环节都有保障，消息几乎不会丢失。
> 如果极端情况丢失，业务上也有补偿机制（如用户可以重新发送验证码）。

**Q3：消费者处理消息失败会一直重试吗？**

> ActiveMQ 默认重试 6 次后会进入死信队列（DLQ），
> 不会无限重试。死信队列中的消息可以人工处理或定期重试。
> 可以通过配置 redeliveryPlugin 调整重试策略。

**Q4：MQ 消息重复消费怎么办？**

> 消费者需要保证"幂等性"——同一条消息处理多次和一次的效果一样。
> 例如：审计日志场景，每条消息带唯一 ID，插入数据库前先查重。
> 邮件场景，同一条验证码发两次也没关系（用户只使用一次）。
