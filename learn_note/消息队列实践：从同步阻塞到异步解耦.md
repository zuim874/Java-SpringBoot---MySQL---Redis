## 一、为什么需要消息队列？

### 1.1 一个直观的例子

假设用户点击"发送验证码"按钮：

```
用户点击 "发送验证码"
    ↓
Controller 接收请求
    ↓
生成 6 位验证码
    ↓
存入 Redis（5 分钟过期）
    ↓
调用邮件服务发送邮件  ← 这里要等 1-3 秒
    ↓
返回 "验证码已发送"

用户等待时间 = 生成验证码 + Redis 写入 + 邮件发送（1-3秒）
```

**问题：** 邮件发送需要 1-3 秒，用户必须等待这段时间才能看到"验证码已发送"的提示。

### 1.2 引入 MQ 后的流程

```
用户点击 "发送验证码"
    ↓
Controller 接收请求
    ↓
生成 6 位验证码
    ↓
存入 Redis（5 分钟过期）
    ↓
把"发送邮件"任务发送到消息队列  ← 这里只要几毫秒
    ↓
立即返回 "验证码已发送"

用户等待时间 = 生成验证码 + Redis 写入 + 消息入队（< 50ms）
```

后台的"消费者"会异步处理邮件发送，用户不需要等待。

### 1.3 MQ 的三大作用

```
┌─────────────────────────────────────────────────────┐
│                  消息队列的三大作用                     │
├─────────────────────────────────────────────────────┤
│  1. 异步解耦：发送方不需要等待接收方处理完成             │
│  2. 削峰填谷：瞬间高流量时，MQ 会缓冲请求，慢慢处理      │
│  3. 可靠通信：消息持久化，即使服务重启也不会丢失          │
└─────────────────────────────────────────────────────┘
```

## 三、技术选型：为什么选 RabbitMQ？

### 3.1 常见消息队列对比

| 特性 | RabbitMQ | Kafka | Redis Stream |
|------|----------|-------|-------------|
| 学习成本 | 低 | 高 | 低 |
| 消息可靠性 | 高（持久化 + 确认机制） | 高 | 中（依赖 Redis） |
| 吞吐量 | 万级/秒 | 百万级/秒 | 万级/秒 |
| 路由灵活度 | 高（多种 Exchange） | 低（Topic 模式） | 低 |
| Spring Boot 支持 | 非常好（Spring AMQP） | 一般 | 一般 |

**选择 RabbitMQ 的原因：**

```
本项目是中小型 Web 应用，特点是：
1. 消息量不大（每天几百封邮件）
2. 需要灵活的路由（不同消息去不同队列）
3. Spring Boot 集成最成熟
4. 运维简单（有 Web 管理界面）

→ RabbitMQ 是最合适的选择
```

### 3.2 备选方案：Redis Stream

如果不想额外安装 RabbitMQ，可以利用项目已有的 Redis 实现 Stream 消息队列：

```
优点：不需要额外安装中间件
缺点：功能不如 RabbitMQ 完善
适用：非常简单的异步任务
```

本文档以 RabbitMQ 为主，附录中也会给出 Redis Stream 的简化方案。

## 四、RabbitMQ 核心概念

### 4.1 三个核心角色

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  Producer │────▶│ Exchange │────▶│  Queue   │────▶│ Consumer │
│ （生产者） │     │ （交换机） │     │ （队列）  │     │ （消费者） │
└──────────┘     └──────────┘     └──────────┘
```

| 角色 | 说明 | 生活中的例子 |
|------|------|------------|
| **Producer** | 发送消息的程序 | 你寄快递 |
| **Exchange** | 根据规则把消息路由到队列 | 快递分拣中心 |
| **Queue** | 存储消息的缓冲区 | 快递仓库 |
| **Consumer** | 接收并处理消息的程序 | 收快递的人 |

### 4.2 Exchange 的四种类型

```
1. Direct Exchange（直连交换机）
   消息发送到 BindingKey 完全匹配的队列
   适用：一对一的消息路由

2. Topic Exchange（主题交换机）
   消息通过通配符匹配（routing.# 匹配 routing.key.xxx）
   适用：一对多的消息路由

3. Fanout Exchange（扇形交换机）
   消息广播到所有绑定的队列
   适用：广播消息（所有服务都收到）

4. Headers Exchange（头交换机）
   根据消息头属性匹配
   适用：复杂的路由规则
```

**本项目主要使用 Direct 和 Fanout 两种类型。**

### 4.3 消息的生命周期

```
生产者发送消息
    ↓
Exchange 接收消息
    ↓
根据 RoutingKey 匹配队列
    ↓
消息存入队列（持久化到磁盘）
    ↓
消费者从队列拉取消息（或 RabbitMQ 推送）
    ↓
消费者处理消息
    ↓
消费者发送 ACK（确认已处理）
    ↓
RabbitMQ 删除消息
```

### 5.1 Docker 安装（推荐）

```bash
# 拉取 RabbitMQ 镜像（带管理界面）

# 启动 RabbitMQ 容器
docker run -d \
  --name rabbitmq \
  -p 5672:5672 \      # AMQP 协议端口（应用连接用）
  -p 15672:15672 \    # Web 管理界面端口
  -e RABBITMQ_DEFAULT_USER=admin \
  -e RABBITMQ_DEFAULT_PASS=123456 \
  rabbitmq:3.13-management
```

4. 启动服务：`net start RabbitMQ`
5. 启用管理界面：`rabbitmq-plugins enable rabbitmq_management`

### 6.3 RabbitMQ 配置类

```java
package com.xuwenye.demo.config.rabbitmq;

import org.springframework.amqp.core.*;
import org.springframework.amqp.rabbit.connection.ConnectionFactory;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.amqp.support.converter.Jackson2JsonMessageConverter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * RabbitMQ 核心配置类
 *
 * 作用：
 * 1. 定义 Exchange、Queue、Binding（路由绑定）
 * 2. 配置消息转换器（Java 对象 ↔ JSON）
 * 3. 配置 RabbitTemplate（发送消息的模板类）
 */
@Configuration
public class RabbitMQConfig {

    // ==================== 交换机名称常量 ====================
    public static final String EXCHANGE_EMAIL = "demo.email.direct";    // 邮件交换机
    public static final String EXCHANGE_AUDIT = "demo.audit.topic";    // 审计日志交换机
    public static final String EXCHANGE_CACHE = "demo.cache.fanout";   // 缓存刷新交换机

    // ==================== 队列名称常量 ====================
    public static final String QUEUE_EMAIL_REGISTER = "demo.email.register";   // 注册验证码邮件
    public static final String QUEUE_EMAIL_RECOVER = "demo.email.recover";     // 恢复账号邮件
    public static final String QUEUE_AUDIT_LOGIN = "demo.audit.login";         // 登录日志
    public static final String QUEUE_AUDIT_OPERATION = "demo.audit.operation"; // 操作日志
    public static final String QUEUE_CACHE_REFRESH = "demo.cache.refresh";     // 缓存刷新

    // ==================== RoutingKey ====================
    public static final String RK_EMAIL_REGISTER = "email.register";
    public static final String RK_EMAIL_RECOVER = "email.recover";
    public static final String RK_AUDIT_LOGIN = "audit.login";
    public static final String RK_AUDIT_OPERATION = "audit.operation.#";

    // ==================== 1. 消息转换器 ====================

    /**
     * Jackson2JsonMessageConverter
     *
     * 作用：把 Java 对象自动转为 JSON 存入消息队列
     * 消费者收到后自动反序列化为 Java 对象
     *
     * 如果不配置这个，默认使用 SimpleMessageConverter（只能传 String 和 byte[]）
     */
    @Bean
    public Jackson2JsonMessageConverter messageConverter() {
        return new Jackson2JsonMessageConverter();
    }

    // ==================== 2. RabbitTemplate ====================

    /**
     * RabbitTemplate 是 Spring AMQP 提供的"发送消息的模板类"
     *
     * 类似 RestTemplate（发 HTTP 请求）和 RedisTemplate（操作 Redis）
     * RabbitTemplate 就是用来"发送消息到 RabbitMQ"的
     */
    @Bean
    public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory,
                                         Jackson2JsonMessageConverter messageConverter) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);
        template.setMessageConverter(messageConverter);

        // 开启 Mandatory（消息无法路由时触发 ReturnCallback）
        template.setMandatory(true);

        // 确认消息是否到达 Exchange（异步回调）
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                System.err.println("消息发送到 Exchange 失败：" + cause);
            }
        });

        // 确认消息是否路由到 Queue
        template.setReturnsCallback(returned -> {
            System.err.println("消息无法路由到队列：" +
                    "Exchange=" + returned.getExchange() +
                    ", RoutingKey=" + returned.getRoutingKey() +
                    ", 原因=" + returned.getReplyText());
        });

        return template;
    }

    // ==================== 3. 定义 Exchange ====================

    /**
     * Direct Exchange：直连交换机
     * 消息根据 RoutingKey 精确匹配队列
     *
     * 适用场景：一个消息发送到一个确定的队列
     * 比如：注册验证码邮件 → 只发送到注册邮件队列
     */
    @Bean
    public DirectExchange emailExchange() {
        return ExchangeBuilder
                .directExchange(EXCHANGE_EMAIL)
                .durable(true)       // 持久化（重启不丢失）
                .build();
    }

    /**
     * Topic Exchange：主题交换机
     * 消息通过通配符匹配（routing.# 匹配 routing.key.xxx）
     *
     * 适用场景：一个消息发送到多个队列
     * 比如：用户登录 → 同时记录到"登录日志"和"操作日志"
     */
    @Bean
    public TopicExchange auditExchange() {
        return ExchangeBuilder
                .topicExchange(EXCHANGE_AUDIT)
                .durable(true)
                .build();
    }

    /**
     * Fanout Exchange：扇形交换机
     * 消息广播到所有绑定的队列
     *
     * 适用场景：所有服务实例都需要收到消息
     * 比如：缓存刷新 → 所有服务实例都收到通知
     */
    @Bean
    public FanoutExchange cacheExchange() {
        return ExchangeBuilder
                .fanoutExchange(EXCHANGE_CACHE)
                .durable(true)
                .build();
    }

    // ==================== 4. 定义 Queue ====================

    /**
     * 队列定义
     *
     * 参数说明：
     * durable: 持久化，重启后队列还在
     * exclusive: 排他，只被当前连接使用（一般不设为 true）
     * autoDelete: 自动删除，没有消费者时是否删除队列
     */
    @Bean
    public Queue emailRegisterQueue() {
        return QueueBuilder.durable(QUEUE_EMAIL_REGISTER).build();
    }

    @Bean
    public Queue emailRecoverQueue() {
        return QueueBuilder.durable(QUEUE_EMAIL_RECOVER).build();
    }

    @Bean
    public Queue auditLoginQueue() {
        return QueueBuilder.durable(QUEUE_AUDIT_LOGIN).build();
    }

    @Bean
    public Queue auditOperationQueue() {
        return QueueBuilder.durable(QUEUE_AUDIT_OPERATION).build();
    }

    @Bean
    public Queue cacheRefreshQueue() {
        return QueueBuilder.durable(QUEUE_CACHE_REFRESH).build();
    }

    // ==================== 5. 绑定关系（Binding） ====================

    /**
     * Binding：把 Queue 绑定到 Exchange，并指定 RoutingKey
     *
     * Direct Exchange：RoutingKey 必须精确匹配
     * Topic Exchange：RoutingKey 可以用通配符
     *   * 匹配一个单词
     *   # 匹配零个或多个单词
     * Fanout Exchange：不需要 RoutingKey（广播到所有绑定的队列）
     */

    // --- 邮件 Direct Exchange ---
    @Bean
    public Binding bindEmailRegister() {
        return BindingBuilder
                .bind(emailRegisterQueue())
                .to(emailExchange())
                .with(RK_EMAIL_REGISTER);
    }

    @Bean
    public Binding bindEmailRecover() {
        return BindingBuilder
                .bind(emailRecoverQueue())
                .to(emailExchange())
                .with(RK_EMAIL_RECOVER);
    }

    // --- 审计 Topic Exchange ---
    @Bean
    public Binding bindAuditLogin() {
        return BindingBuilder
                .bind(auditLoginQueue())
                .to(auditExchange())
                .with(RK_AUDIT_LOGIN);
    }

    @Bean
    public Binding bindAuditOperation() {
        return BindingBuilder
                .bind(auditOperationQueue())
                .to(auditExchange())
                .with(RK_AUDIT_OPERATION);
    }

    // --- 缓存 Fanout Exchange ---
    @Bean
    public Binding bindCacheRefresh() {
        return BindingBuilder
                .bind(cacheRefreshQueue())
                .to(cacheExchange());
    }
}
```

### 7.2 引入 MQ 后的代码

**第一步：定义消息体（DTO）**

```java
package com.xuwenye.demo.dto.mq;

/**
 * 邮件消息体
 *
 * 为什么需要 DTO？
 * 1. 消息在网络上传输，需要序列化（Java 对象 → JSON）
 * 2. DTO 明确规定了消息的格式，生产者和消费者之间约定清晰
 * 3. 后续修改消息格式时，只需要改 DTO，不需要改所有调用方
 */
public class EmailMessage {

    /** 邮件类型：REGISTER（注册验证码）、RECOVER（恢复账号） */
    private String type;

    /** 收件人邮箱 */
    private String email;

    /** 验证码 */
    private String code;

    /** 发送时间 */
    private String timestamp;

    public EmailMessage() {}

    public EmailMessage(String type, String email, String code) {
        this.type = type;
        this.email = email;
        this.code = code;
        this.timestamp = java.time.LocalDateTime.now().toString();
    }

    // Getters & Setters（省略，实际代码需要）
    public String getType() { return type; }
    public void setType(String type) { this.type = type; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public String getCode() { return code; }
    public void setCode(String code) { this.code = code; }
    public String getTimestamp() { return timestamp; }
}
```

**第二步：改造生产者（发送方）**

```java
// AuthController.java 改造后
@RestController
@RequestMapping("/api/auth")
public class AuthController {

    private final RabbitTemplate rabbitTemplate;  // 注入 RabbitTemplate

    public AuthController(RabbitTemplate rabbitTemplate, /* 其他依赖 */) {
        this.rabbitTemplate = rabbitTemplate;
        // ...
    }

    @PostMapping("/send-registercode")
    public Result<?> sendVerificationCode(@RequestParam String email) {
        // ... 校验逻辑（不变） ...

        String code = generateVerificationCode.generateVerificationCode();
        redisUtil.set(redisKey, code, 5, TimeUnit.MINUTES);

        // 不再直接调用 emailUtil，而是发送消息到 MQ
        // 用户不需要等待邮件发送完成
        EmailMessage message = new EmailMessage("REGISTER", email, code);
        rabbitTemplate.convertAndSend(
            RabbitMQConfig.EXCHANGE_EMAIL,      // Exchange
            RabbitMQConfig.RK_EMAIL_REGISTER,    // RoutingKey
            message                              // 消息体（自动转 JSON）
        );

        return Result.ok("注册验证码已发送到您的邮箱，请注意查收");
    }
}
```

**第三步：创建消费者（接收方）**

```java
package com.xuwenye.demo.mq.consumer;

import com.rabbitmq.client.Channel;
import com.xuwenye.demo.dto.mq.EmailMessage;
import com.xuwenye.demo.util.email.EmailUtil;
import org.springframework.amqp.core.Message;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;

/**
 * 邮件消费者
 *
 * @RabbitListener：声明这是一个 MQ 消费者
 * queues：指定监听哪个队列
 *
 * 当队列中有消息时，RabbitMQ 会自动调用这个方法
 */
@Component
public class EmailConsumer {

    private final EmailUtil emailUtil;

    public EmailConsumer(EmailUtil emailUtil) {
        this.emailUtil = emailUtil;
    }

    /**
     * 处理注册验证码邮件
     *
     * 参数说明：
     * message: 消息体（自动从 JSON 反序列化为 Java 对象）
     * channel: 通信通道（用于手动 ACK）
     * deliveryTag: 消息的唯一标识（用于 ACK 时告诉 RabbitMQ 是哪条消息）
     */
    @RabbitListener(queues = RabbitMQConfig.QUEUE_EMAIL_REGISTER)
    public void handleRegisterEmail(EmailMessage message,
                                    Channel channel,
                                    org.springframework.amqp.core.Message rawMessage) {
        try {
            long deliveryTag = rawMessage.getMessageProperties().getDeliveryTag();

            // 根据邮件类型发送
            switch (message.getType()) {
                case "REGISTER":
                    emailUtil.sendRegisterVerificationCode(
                        message.getEmail(), message.getCode());
                    break;
                case "RECOVER":
                    emailUtil.sendRecoverAccountCode(
                        message.getEmail(), message.getCode());
                    break;
                default:
                    System.err.println("未知的邮件类型：" + message.getType());
            }

            // 手动 ACK：告诉 RabbitMQ 消息已处理完毕，可以删除
            // 第一个参数：deliveryTag（消息标识）
            // 第二个参数：multiple（是否批量确认，false 表示只确认这一条）
            channel.basicAck(deliveryTag, false);

            System.out.println("邮件发送成功：" + message.getEmail());

        } catch (Exception e) {
            System.err.println("邮件发送失败：" + e.getMessage());

            try {
                // 处理失败，拒绝消息并要求重新入队
                // 第三个参数：requeue（是否重新入队）
                // true 表示重新入队，等待再次消费
                // false 表示丢弃或进入死信队列
                channel.basicNack(
                    rawMessage.getMessageProperties().getDeliveryTag(),
                    false,
                    true  // 重新入队，重试
                );
            } catch (Exception ex) {
                ex.printStackTrace();
            }
        }
    }
}
```

### 7.3 改造前后的对比

```
改造前（同步）：
Controller → 生成验证码 → 存入 Redis → 发送邮件（等待1-3秒）→ 返回响应
```

## 九、场景 3：缓存刷新与一致性

### 9.1 现状问题

```
当前缓存刷新方式：
写操作（更新用户信息）→ 删除 Redis 缓存 → 直接返回

问题：
1. 如果在集群部署（多台服务器），A 服务器删除了缓存
   B 服务器可能还在用旧缓存
2. 删除缓存的操作是"发了就忘"，没有确认机制
```

### 9.2 使用 Fanout Exchange 广播缓存刷新

```
写操作（任何服务器）
    ↓
发送缓存刷新消息到 Fanout Exchange
    ↓
所有服务器实例都收到消息
    ↓
每台服务器各自删除本地缓存
```

### 9.3 生产者：在 UserService 中发送缓存刷新消息

```java
// UserService.java 改造后
@Service
public class UserService {

    private final RabbitTemplate rabbitTemplate;  // 注入

    public UserService(RabbitTemplate rabbitTemplate, /* 其他依赖 */) {
        this.rabbitTemplate = rabbitTemplate;
    }

    // 删除用户后刷新缓存
    public boolean deleteById(Long id) {
        User user = userMapper.selectById(id);
        boolean result = userMapper.deleteById(id) > 0;

        if (result && user != null) {
            // 本地删除缓存
            redisTemplate.delete("demo:user:login:active:" + user.getUsername());
            redisTemplate.delete("demo:user:login:all:" + user.getUsername());

            // 广播通知其他服务实例也刷新缓存
            rabbitTemplate.convertAndSend(
                RabbitMQConfig.EXCHANGE_CACHE,
                "",  // Fanout Exchange 不需要 RoutingKey
                "cache_refresh:user:" + user.getUsername()
            );
        }
        return result;
    }
}
```

### 9.4 消费者：刷新缓存

```java
package com.xuwenye.demo.mq.consumer;

import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Component;
import com.rabbitmq.client.Channel;
import org.springframework.amqp.core.Message;

/**
 * 缓存刷新消费者
 *
 * 收到缓存刷新通知后，删除本地 Redis 中的缓存
 */
@Component
public class CacheRefreshConsumer {

    private final RedisTemplate<String, Object> redisTemplate;

    public CacheRefreshConsumer(RedisTemplate<String, Object> redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    @RabbitListener(queues = RabbitMQConfig.QUEUE_CACHE_REFRESH)
    public void handleCacheRefresh(String message,
                                   Channel channel,
                                   Message rawMessage) {
        try {
            // 消息格式：cache_refresh:user:admin
            // 提取出要刷新的缓存 key
            String cacheKey = message.replace("cache_refresh:", "");

            // 删除对应的缓存
            Set<String> keys = redisTemplate.keys("demo:user:login:*:" + cacheKey);
            if (keys != null && !keys.isEmpty()) {
                redisTemplate.delete(keys);
                System.out.println("缓存已刷新：" + keys);
            }

            channel.basicAck(rawMessage.getMessageProperties().getDeliveryTag(), false);
        } catch (Exception e) {
            System.err.println("缓存刷新失败：" + e.getMessage());
        }
    }
}
```

## 十一、MQ 的可靠性保障

### 11.1 消息丢失的场景

```
消息从发送到消费，经过三个环节：

生产者 → RabbitMQ → 消费者

每个环节都可能丢失消息：
1. 生产者发送时网络中断 → 消息没到 RabbitMQ
2. RabbitMQ 收到后宕机 → 消息丢失（如果没持久化）
3. 消费者收到后崩溃 → 消息丢失（如果自动 ACK）
```

### 11.2 解决方案：三层保障

```
第一层：生产者确认（Publisher Confirm）
    消息发送到 Exchange 后，RabbitMQ 会回调确认
    如果没收到确认，生产者可以重发

第二层：消息持久化（Message Persistence）
    消息写入磁盘，RabbitMQ 重启后消息还在
    配置：deliveryMode = PERSISTENT

第三层：消费者手动 ACK（Manual Acknowledge）
    消费者处理完消息后才发送 ACK
    如果处理失败，消息重新入队
```

### 11.3 配置代码

```yaml
# application.yml 中已配置
spring:
  rabbitmq:
    publisher-confirm-type: correlated    # 生产者确认
    publisher-returns: true               # 消息路由确认
    listener:
      simple:
        acknowledge-mode: manual          # 手动 ACK
        retry:
          enabled: true                   # 重试机制
          max-attempts: 3                 # 最多重试 3 次
```

### 11.4 消费失败的处理策略

```
消费者处理消息失败
    ↓
重试 3 次（默认间隔 2 秒）
    ↓
还是失败
    ↓
┌──────────────────────────────────────────────┐
│            两种处理方式                         │
├──────────────────────────────────────────────┤
│  方式1：记录日志 + 丢弃消息                     │
│  适用：非关键消息（如审计日志）                   │
│                                              │
│  方式2：进入死信队列（Dead Letter Queue）       │
│  适用：关键消息（如订单、支付）                   │
│  人工介入处理                                   │
└──────────────────────────────────────────────┘
```

## 十三、总结与心得

### 13.1 引入 MQ 后的架构变化

```
引入 MQ 前：
Controller → Service → EmailUtil（同步）
                 ↓
            Redis / MySQL

引入 MQ 后：
Controller → Service → RabbitTemplate（异步，几毫秒）
                 ↓
            Redis / MySQL
                 ↓
           RabbitMQ 队列
                 ↓
           Consumer（后台处理）
```

### 13.2 核心价值

```
1. 用户体验提升
   验证码发送从等待 1-3 秒 → 瞬间返回

2. 系统解耦
   邮件服务挂了不影响注册流程
   邮件服务恢复后自动处理积压消息

3. 可扩展性
   新增功能只需要加新的消费者
   不需要修改现有代码

4. 削峰填谷
   瞬间大量注册请求时，MQ 缓冲消息
   消费者按自己的节奏处理，不会压垮邮件服务器
```

### 13.3 注意事项

```
1. 不要滥用 MQ
   简单操作（如密码加密）不需要 MQ
   只有耗时操作（邮件、日志）才适合

2. 消息幂等性
   消费者可能处理同一条消息多次
   确保重复处理不会产生副作用

3. 监控告警
   关注队列积压情况
   消息堆积过多说明消费者处理不过来

4. 消息大小
   不要发送大消息（如 > 10MB）
   大消息用文件存储，MQ 只传文件路径
```

### 13.4 面试常见问题

**Q1：为什么用 RabbitMQ 而不是 Kafka？**

> 本项目是中小型 Web 应用，每天消息量在几百到几千条级别。
> RabbitMQ 的吞吐量完全够用，而且 Spring Boot 集成最成熟，
> 运维简单（有 Web 管理界面）。
> Kafka 适合每天几百万条消息的大数据场景，对这个项目来说太重了。

**Q2：MQ 消息丢失了怎么办？**

> 三层保障：生产者确认（Confirm）、消息持久化（Persistent）、
> 消费者手动 ACK。三个环节都有保障，消息几乎不会丢失。
> 如果极端情况丢失，业务上也有补偿机制（如用户可以重新发送验证码）。

**Q3：消费者处理消息失败会一直重试吗？**

> 默认配置重试 3 次，间隔 2 秒。
> 3 次都失败后，消息会进入死信队列（Dead Letter Queue），
> 不会无限重试。死信队列中的消息可以人工处理或定期重试。

**Q4：MQ 消息重复消费怎么办？**

> 消费者需要保证"幂等性"——同一条消息处理多次和一次的效果一样。
> 例如：审计日志场景，每条消息带唯一 ID，插入数据库前先查重。
> 邮件场景，同一条验证码发两次也没关系（用户只使用一次）。
