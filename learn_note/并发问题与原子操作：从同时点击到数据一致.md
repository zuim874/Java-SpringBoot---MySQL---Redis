## 一、为什么要关心并发？

### 1.1 一个简单的例子

假设你写了一个银行转账功能：

```java
// 转账：从 A 账户转 100 元到 B 账户
if (accountA.getBalance() >= 100) {
    accountA.setBalance(accountA.getBalance() - 100);
    accountB.setBalance(accountB.getBalance() + 100);
}
```

**如果只有一个用户操作，这个代码没问题。**

**但如果两个用户同时操作呢？**

```
时间线：
T1: 用户1 读取 A 余额：1000元
T2: 用户2 读取 A 余额：1000元
T3: 用户1 判断：1000 >= 100，可以转账
T4: 用户2 判断：1000 >= 100，可以转账
T5: 用户1 执行：A 余额 = 900，B 余额增加100
T6: 用户2 执行：A 余额 = 900，B 余额又增加100
T7: 最终结果：A 余额 = 900（应该剩800），B 余额多了100
```

**这就是并发问题：** 多个线程同时操作同一份数据，导致结果不符合预期。

### 1.2 并发问题的三个条件

并发问题通常需要同时满足三个条件：

| 条件 | 解释 | 生活中的例子 |
|------|------|------------|
| **原子性** | 一个操作被中途打断 | 你取钱时，ATM 到一半断电了 |
| **可见性** | 一个线程的修改，另一个线程看不到 | 两个人同时改一份 Excel，保存时互相覆盖 |
| **有序性** | 编译器优化导致代码执行顺序变化 | 你写了"先交钱再发货"，但编译器优化成"先发货再交钱" |

**本项目的并发问题，主要涉及"原子性"的破坏。**

## 三、并发问题 1：注册重复用户

### 3.1 问题代码

```java
// AuthController.java 第 80-120 行
// 检查用户名是否已存在
if (userService.findUsername(username) != null) {
    return Result.error(400, "用户名已存在");
}

// ... 中间还有密码校验、验证码校验等逻辑 ...

// 保存用户
User user = new User();
user.setUsername(username);
boolean saved = userService.save(user);
```

### 3.2 并发场景

```
时间线：
T1: 线程A 执行 findUsername("admin") → 返回 null（不存在）
T2: 线程B 执行 findUsername("admin") → 返回 null（不存在）
T3: 线程A 执行 save(user) → 插入成功，username = "admin"
T4: 线程B 执行 save(user) → 插入失败！MySQL 报唯一键冲突

    线程A 收到：200 注册成功
    线程B 收到：500 服务器内部错误（DuplicateKeyException）
```

### 3.3 为什么说这是"检查-插入"模式？

```java
// 经典的"检查-操作"（Check-Then-Act）模式
if (检查条件) {     // 步骤1：检查（读）
    执行操作;       // 步骤2：操作（写）
}
```

**问题在于：** 步骤1和步骤2之间，其他线程可以插入数据。

### 3.4 现有保护机制

MySQL 的 `username` 字段有 **唯一索引**（UNIQUE），所以线程B的 `save()` 会抛出 `DuplicateKeyException`。

**但问题是：** 线程B收到的不是"用户名已存在"的提示，而是 500 服务器错误，用户体验很差。

### 3.5 解决方案

**方案一：数据库唯一约束 + 异常捕获（推荐，最简单的防御）**

```java
public Result<?> register(...) {
    // 先检查（能拦住大部分情况）
    if (userService.findUsername(username) != null) {
        return Result.error(400, "用户名已存在");
    }
    
    try {
        boolean saved = userService.save(user);
        if (saved) {
            return Result.ok("注册成功");
        }
    } catch (DuplicateKeyException e) {
        // 兜底：并发情况下唯一键冲突
        return Result.error(400, "用户名已存在");
    }
    return Result.error(500, "注册失败");
}
```

**方案二：数据库唯一约束 + 唯一索引（兜底，必须要有）**

```sql
-- username 字段必须有唯一索引
CREATE UNIQUE INDEX idx_username ON sys_user(username);
```

**方案三：分布式锁（最严谨，但成本高）**

```
操作前先获取锁：lock("register:admin")
    如果获取失败 → 有人正在注册这个用户名 → 返回"请稍后重试"
    如果获取成功 → 执行检查+插入操作
    操作完成后 → 释放锁
```

**最佳实践：方案一 + 方案二组合使用。**

## 四、并发问题 2：验证码发送绕过频率限制

### 4.1 问题代码

```java
// AuthController.java 第 140-158 行（简化）
public Result<?> sendVerificationCode(@RequestParam String email) {
    String sendLimitKey = "verify_registerCode_limit:" + email;
    
    // 步骤1：检查是否在60秒内重复发送
    if (redisUtil.hasKey(sendLimitKey)) {
        long ttl = redisUtil.getExpire(sendLimitKey, TimeUnit.SECONDS);
        return Result.error(400, "请等待 " + ttl + " 秒后再试");
    }
    
    // 步骤2：生成验证码并存入 Redis
    String code = generateVerificationCode();
    redisUtil.set(sendLimitKey, "1", 60, TimeUnit.SECONDS);
    redisUtil.set(redisKey, code, 5, TimeUnit.MINUTES);
    
    // 步骤3：发送邮件
    emailUtil.sendRegisterVerificationCode(email, code);
}
```

### 4.2 并发场景

```
时间线：
T1: 线程A：hasKey("verify_registerCode_limit:xxx@email.com") → false
T2: 线程B：hasKey("verify_registerCode_limit:xxx@email.com") → false
T3: 线程A：set("verify_registerCode_limit:xxx@email.com", "1", 60) → 设置限制标记
T4: 线程B：set("verify_registerCode_limit:xxx@email.com", "1", 60) → 覆盖限制标记
T5: 线程A：发送验证码 "123456" 到邮箱
T6: 线程B：发送验证码 "654321" 到邮箱

    用户收到两条验证码，且后设置的会覆盖前面的
    实际上用户只应该收到一条！
```

### 4.3 问题本质

同样的问题模式：**"检查-设置"（Check-Then-Set）**

```java
if (redisUtil.hasKey(key)) {  // 步骤1：检查（读）
    return Result.error(400, "请稍后再试");
}
redisUtil.set(key, value);    // 步骤2：设置（写）
```

### 4.4 解决方案：Redis SET NX（原子操作）

**核心思路：** 把"检查"和"设置"合并成一个原子操作。

Redis 提供了 `SET NX`（SET if Not eXists）命令：

```bash
# 如果 key 不存在才设置，设置成功返回 OK，失败返回 nil
SET key value NX EX 60
```

**在 RedisUtil 中新增方法：**

```java
// RedisUtil.java 新增方法
public Boolean setIfAbsent(String key, String value, long timeout, TimeUnit unit) {
    return redisTemplate.opsForValue()
            .setIfAbsent(key, value, timeout, unit);
}
```

**修改后的代码：**

```java
public Result<?> sendVerificationCode(String email) {
    String sendLimitKey = "verify_registerCode_limit:" + email;
    
    // 原子操作：SET NX + EX（不存在才设置，设置60秒过期）
    Boolean success = redisUtil.setIfAbsent(
        sendLimitKey, "1", 60, TimeUnit.SECONDS
    );
    
    // setIfAbsent 返回 false 表示 key 已存在（60秒内已发过）
    if (Boolean.FALSE.equals(success)) {
        long ttl = redisUtil.getExpire(sendLimitKey, TimeUnit.SECONDS);
        return Result.error(400, "请等待 " + ttl + " 秒后再试");
    }
    
    // 到这里，限制标记已成功设置，不会出现并发问题
    String code = generateVerificationCode();
    redisUtil.set(redisKey, code, 5, TimeUnit.MINUTES);
    emailUtil.sendRegisterVerificationCode(email, code);
    
    return Result.ok("验证码已发送");
}
```

### 4.5 两种方式的对比

| 方式 | 代码 | 是否原子 | 并发安全 |
|------|------|---------|---------|
| 原来的方式 | `hasKey()` + `set()` | ❌ 两步操作 | ❌ 不安全 |
| SET NX | `setIfAbsent()` | ✅ 一步操作 | ✅ 安全 |

**为什么 setIfAbsent 是原子的？**

```
Redis 是单线程处理命令的。

当客户端发送 "SET key value NX EX 60" 时：
1. Redis 在主线程中执行这个命令
2. 检查 key 是否存在
3. 如果不存在，设置 key 和过期时间
4. 返回 OK

在整个过程中，不会有其他命令插入执行。
所以"检查"和"设置"是原子的一步操作。
```

## 五、并发问题 3：删除和恢复同时操作

### 5.1 问题代码

```java
// UserService.java 第 192-229 行

// 删除用户（逻辑删除，设置 is_deleted = 1）
public boolean deleteById(Long id) {
    User user = userMapper.selectById(id);  // 先查
    boolean result = userMapper.deleteById(id) > 0;  // 再删
    // ... 清理缓存 ...
    return result;
}

// 恢复用户（设置 is_deleted = 0）
public boolean recoverById(Long id) {
    boolean result = userMapper.recoverById(id) > 0;  // 恢复
    // ... 刷新缓存 ...
    return result;
}
```

### 5.2 并发场景

```
时间线：
T1: 管理员A 执行 deleteById(1) → 设置 is_deleted = 1
T2: 管理员B 执行 recoverById(1) → 设置 is_deleted = 0
T3: 管理员A 的缓存清理 → 清理了缓存
T4: 管理员B 的缓存刷新 → 写入缓存

    最终状态取决于 T3 和 T4 的先后顺序
    可能缓存中存的是"已恢复"的数据，但数据库有延迟
    也可能缓存为空，导致下次查询走数据库
```

### 5.3 问题本质

**"读-写-写"冲突：** 两个线程同时写同一行数据，且其中还有读操作。

### 5.4 解决方案

**方案一：乐观锁（版本号机制）**

在数据库表中加一个 `version` 字段：

```sql
ALTER TABLE sys_user ADD COLUMN version INT DEFAULT 0;
```

更新时带上版本号：

```java
@Update("UPDATE sys_user SET is_deleted = 1, version = version + 1 WHERE id = #{id} AND version = #{version}")
int deleteByIdWithVersion(@Param("id") Long id, @Param("version") Integer version);

@Update("UPDATE sys_user SET is_deleted = 0, version = version + 1 WHERE id = #{id} AND version = #{version}")
int recoverByIdWithVersion(@Param("id") Long id, @Param("version") Integer version);
```

**工作原理：**

```
初始状态：id=1, version=0

T1: 管理员A 读取 version=0
T2: 管理员B 读取 version=0
T3: 管理员A 执行 UPDATE ... WHERE id=1 AND version=0 → 成功，version变成1
T4: 管理员B 执行 UPDATE ... WHERE id=1 AND version=0 → 失败！因为version已经是1了
```

**方案二：数据库行锁（悲观锁）**

```java
// 查询时加锁：SELECT ... FOR UPDATE
@Select("SELECT * FROM sys_user WHERE id = #{id} FOR UPDATE")
User selectByIdWithLock(@Param("id") Long id);
```

**方案三：业务层面判断（最简单）**

对于删除/恢复场景，如果最终状态是一致的，其实问题不大：

```
删除 + 删除 = 删除（幂等）
恢复 + 恢复 = 恢复（幂等）
删除 + 恢复 = 取决于最后一次操作
```

### 5.5 三种方案对比

| 方案 | 复杂度 | 性能 | 适用场景 |
|------|--------|------|---------|
| 乐观锁（版本号） | 中 | 高（读不加锁） | 读多写少 |
| 悲观锁（FOR UPDATE） | 低 | 低（读也加锁） | 写多读少 |
| 业务判断（幂等设计） | 低 | 高 | 操作可覆盖的场景 |

## 六、并发问题 4：缓存与数据库不一致

### 6.1 缓存-Aside 模式

本项目使用"缓存-Aside"（Cache-Aside）模式，这是最常用的缓存策略：

```
读操作：
1. 先查 Redis
2. 有数据 → 直接返回（缓存命中）
3. 没数据 → 查 MySQL
4. 查到后写入 Redis（设置过期时间）

写操作：
1. 更新 MySQL
2. 删除 Redis 中的缓存
```

### 6.2 问题代码

```java
// UserService.java 第 23-46 行
public User findUsernameforlogin(String username) {
    String cacheKey = "demo:user:login:active:" + username;
    
    // 第 1 步：先从 Redis 查
    User cached = (User) redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return cached;  // 缓存命中，直接返回
    }
    
    // 第 2 步：Redis 没有，查 MySQL
    User user = userMapper.selectOne(wrapper);
    
    // 第 3 步：查到了就写入 Redis
    if (user != null) {
        redisTemplate.opsForValue().set(cacheKey, user, 10, TimeUnit.MINUTES);
    }
    return user;
}
```

### 6.3 并发场景

```
时间线：
T1: 线程A（写操作）：更新 MySQL → 用户昵称改为"新名字"
T2: 线程A（写操作）：删除 Redis 缓存
T3: 线程B（读操作）：查询 Redis → 缓存已被删除（miss）
T4: 线程C（写操作）：更新 MySQL → 用户昵称改为"另一个名字"
T5: 线程B（读操作）：查询 MySQL → 读到"新名字"（T1 更新的）
T6: 线程C（写操作）：删除 Redis 缓存
T7: 线程B（读操作）：写入 Redis → 缓存存的是"新名字"
T8: 线程C（写操作）：删除 Redis 缓存（已删除）

    最终：T7 写入的"新名字"在缓存中
    但实际上数据库的最新值是"另一个名字"
    
    但因为有 10 分钟的过期时间，10 分钟后缓存自动失效
    下次查询会重新从数据库读，数据恢复一致
```

### 6.4 这个问题严重吗？

**不严重，但需要了解原因：**

| 因素 | 说明 |
|------|------|
| 过期时间 | 缓存有 10 分钟过期，过期后自动恢复一致 |
| 并发概率 | 需要"读"和"写"同时发生，概率较低 |
| 影响范围 | 用户看到的是旧数据，不会导致数据丢失 |

**这是缓存-Aside 模式的固有缺陷，业界普遍接受。**

### 6.5 解决方案

**方案一：延迟双删（先删缓存，再删一次）**

```
写操作：
1. 先删除 Redis 缓存
2. 更新 MySQL
3. 休眠一小段时间（如 500ms）
4. 再次删除 Redis 缓存
```

**方案二：设置较短的过期时间（本项目已采用）**

本项目缓存的过期时间是 10 分钟，即使出现不一致，10 分钟后也会自动恢复。

**方案三：使用 Redis 分布式锁，让读写串行化**

```
读操作：
1. 获取锁（lock:user:admin）
2. 查 Redis
3. 如果没查到，查 MySQL 并写入 Redis
4. 释放锁

写操作：
1. 获取锁（lock:user:admin）
2. 更新 MySQL
3. 删除 Redis 缓存
4. 释放锁
```

**本项目现状：** 10 分钟过期时间 + 低并发概率 = 可以接受。

## 七、并发问题 5：项目启动时重复创建管理员

### 7.1 问题代码

```java
// InitAdminRunner.java 第 31-39 行
if (userService.findUsername("admin") == null) {
    User admin = new User();
    admin.setUsername("admin");
    admin.setPassword(passwordEncoder.encode("123456"));
    admin.setNickname("超级管理员");
    userService.save(admin);
}
```

### 7.2 并发场景

**这个代码在单机运行时没有问题。** `CommandLineRunner` 是单线程执行的。

**但在以下场景会有问题：**

| 场景 | 问题 |
|------|------|
| 多实例部署（两台服务器同时启动） | 两个实例同时检查 admin 不存在，都插入 |
| 手动重启时未清库 | 数据库已有数据，findUsername 能查到，不会重复插入 |

### 7.3 解决方案

**方案一：INSERT IGNORE / ON DUPLICATE KEY UPDATE**

```sql
-- 如果 username 已存在，忽略插入
INSERT IGNORE INTO sys_user (username, password, nickname, ...) VALUES (?, ?, ?, ...);

-- 或者：如果存在就更新
INSERT INTO sys_user (...) VALUES (...) ON DUPLICATE KEY UPDATE nickname = VALUES(nickname);
```

**方案二：使用数据库唯一索引兜底（本项目已具备）**

```sql
-- 确保 username 有唯一索引
CREATE UNIQUE INDEX idx_username ON sys_user(username);
```

**方案三：启动时不创建，改为手动初始化**

提供一个专门的初始化接口，管理员手动调用：

```java
@PostMapping("/api/admin/init")
public Result<?> initAdmin() {
    if (userService.findUsername("admin") != null) {
        return Result.error(400, "管理员已存在，无需初始化");
    }
    userService.save(admin);
    return Result.ok("初始化成功");
}
```

## 八、原子操作的核心概念

### 8.1 原子操作的定义

**原子操作（Atomic Operation）** 是指"不可中断的操作"——要么全部执行完，要么完全不执行。

```
原子操作就像"转账"：
    ✅ 扣钱 + 加钱 要么都成功，要么都失败（原子）
    ❌ 扣钱成功，但加钱失败 → 钱丢了（非原子）
```

### 8.2 实现原子操作的三种方式

**1. 数据库层面：**

```sql
-- 单条 SQL 语句本身就是原子的
UPDATE sys_user SET is_deleted = 1 WHERE id = 1;

-- CAS（Compare And Swap）：带条件的原子更新
UPDATE sys_user SET is_deleted = 1, version = version + 1 
WHERE id = 1 AND version = 0;
```

**2. Redis 层面：**

```bash
# SET NX：不存在才设置，原子操作
SET key value NX EX 60

# Lua 脚本：自定义原子操作
EVAL "if redis.call('GET', KEYS[1]) then return 0 else redis.call('SET', KEYS[1], ARGV[1]) return 1 end" 1 key value
```

**3. Java 层面：**

```java
// synchronized 关键字
public synchronized void doSomething() {
    // 同一时间只有一个线程能进入这个方法
}

// ReentrantLock
private final Lock lock = new ReentrantLock();
public void doSomething() {
    lock.lock();
    try {
        // 同一时间只有一个线程能执行这里的代码
    } finally {
        lock.unlock();
    }
}
```

### 8.3 分布式锁（跨多台服务器的原子操作）

当应用部署在多台服务器上时，`synchronized` 和 `ReentrantLock` 就不够用了（它们只在单个 JVM 内有效）。

**分布式锁的原理：**

```
服务器A 获取锁 → 成功 → 执行操作 → 释放锁
服务器B 获取锁 → 失败 → 等待或返回错误
服务器C 获取锁 → 失败 → 等待或返回错误
```

**Redis 实现分布式锁（最常用）：**

```java
// 获取锁（SET NX + 过期时间，防止死锁）
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent("lock:register:admin", "1", Duration.ofSeconds(10));

if (Boolean.TRUE.equals(locked)) {
    try {
        // 执行需要保护的操作
        // ...
    } finally {
        // 释放锁
        redisTemplate.delete("lock:register:admin");
    }
}
```

## 十一、总结与面试常见问题

### 11.1 核心知识点

```
并发问题的本质：检查-操作模式（Check-Then-Act）
    ↓
解决方案的本质：把检查和操作合并成原子操作
    ↓
实现原子操作的三种方式：
├── 数据库层面：单条 SQL、CAS（乐观锁）、FOR UPDATE（悲观锁）
├── Redis 层面：SET NX、事务、Lua 脚本
└── Java 层面：synchronized、ReentrantLock、分布式锁
```

### 11.2 本项目最重要的三个修改

| 优先级 | 修改 | 原因 |
|--------|------|------|
| 1 | 注册接口添加 `DuplicateKeyException` 捕获 | 避免用户看到 500 错误 |
| 2 | 验证码发送改用 `setIfAbsent` 原子操作 | 避免用户收到多条验证码 |
| 3 | 数据库唯一索引（确保已有） | 最终防线，防止数据重复 |

### 11.3 面试常见问题

**Q1：什么是"检查-操作"模式？为什么会有并发问题？**

> 检查-操作模式是指：先检查某个条件是否满足，再执行操作。
> 比如"检查用户名是否存在，再插入用户"。
> 并发问题发生在检查之后、操作之前，另一个线程修改了数据。
> 因为没有原子性，检查结果在操作执行时已经过时了。

**Q2：Redis 的 SET NX 为什么是原子的？**

> Redis 是单线程处理命令的。当执行 SET NX 时，
> 从"检查 key 是否存在"到"设置 key 和过期时间"，
> 中间不会有其他命令插入，所以是原子的。

**Q3：乐观锁和悲观锁有什么区别？**

> 乐观锁：假设不会发生冲突，操作时再检查（版本号机制）。
> 适用于读多写少的场景，性能好。
>
> 悲观锁：假设一定会发生冲突，操作前先加锁（FOR UPDATE）。
> 适用于写多读少的场景，性能差但安全。

**Q4：缓存和数据库不一致怎么解决？**

> 最常用的方案是"缓存-Aside"模式 + 过期时间。
> 即使出现不一致，过期后也会自动恢复。
> 如果需要更严格的保证，可以用"延迟双删"或分布式锁。
> 但大多数业务场景下，短暂的不一致是可以接受的。

**Q5：synchronized 和分布式锁有什么区别？**

> synchronized 只在单个 JVM 内有效。
> 如果应用部署在多台服务器上，synchronized 无法跨服务器同步。
> 分布式锁（如 Redis 实现的锁）可以跨多台服务器工作。
> 分布式锁的代价更高（需要网络通信），所以能用 synchronized 就不用分布式锁。

> 但理解这些概念对于编写可靠的代码至关重要。
> 并发问题就像"地雷"——你不知道它什么时候会爆炸，
> 但你知道它存在，就应该在代码中埋好"防护措施"。
