========== 问题：
Profile 个人中心 -> 注销账号 -> 点击"发送验证码"，前端一直提示
    "网络错误，请检查后端服务是否启动"
但用命令行直连后端调用同一接口完全正常（返回 200 + 验证码已发送）。
之前的会话中还出现过"发送验证码会弹出新页面（跳转到登录页）"的现象。

========== 排查过程：

第一层：直连后端验证（数据/业务层正常）
带有效 token 调用 send-deletecode：
    POST http://localhost:8080/api/user/send-deletecode   => HTTP 200
        {"code":200,"mes":"成功","data":"账号注销验证码已发送到您的邮箱，请注意查收"}
    POST http://localhost:8081/api/user/send-deletecode（经 nginx）=> HTTP 200 同上

结论：后端代码、业务逻辑、nginx 转发全部正常，"网络错误"是前端行为。

第二层：无 token 访问的响应（401 空 body）
不带 token 调用同一接口：
    POST http://localhost:8080/api/user/send-deletecode   => HTTP 401，body 为空
说明：send-deletecode 在 SecurityConfig 未放行（需登录），未认证返回 401；
且 401 的 body 为空（authenticationEntryPoint 的 JSON 未生效，后端尚未重启）。

第三层：读 request.js 的 401 处理（找到根因）
    if (res.status === 401 && !isPublicRequest) {
        localStorage.removeItem('token')
        localStorage.removeItem('nickname')
        window.location.href = '/login'
        return            // <-- 返回 undefined！
    }
当 token 过期/无效时：后端 401 -> 前端跳转登录页 -> return undefined。

第四层：读 ProfileView 的调用处（确认 TypeError）
    const data = await request('/user/send-deletecode', { ... })
    if (data.code === 200) { ... }      // <-- data 是 undefined！
    else { ... }
data 为 undefined 时访问 data.code 抛 TypeError（Cannot read properties of undefined），
被外层 catch 捕获后统一显示成误导性的"网络错误，请检查后端服务是否启动"。

第五层：关联上一轮"弹出新页面"
401 跳转 window.location.href = '/login' 就是用户看到的"弹出新页面/跳到登录页"。
两轮问题同源：都是 token 过期/无效 -> 401 -> request.js 处理不当。

========== 根因汇总：
1. request.js 的 401 分支 return undefined，调用方拿不到响应对象
2. 各页面直接访问 data.code 未判空 -> TypeError
3. catch 把 TypeError 兜底显示成"网络错误，请检查后端服务是否启动"（误导）
4. 附带发现：send-deletecode 的 @RateLimit(maxRequests=1) 太严，60 秒内第二次点击就
   429"发送频繁"；且弹窗内没有消息显示区，服务反馈显示在主页被遮罩盖住

========== 解决方案：
1. request.js：401 跳转后返回明确对象，不再返回 undefined
    // 修改前
    if (res.status === 401 && !isPublicRequest) {
        localStorage.removeItem('token')
        localStorage.removeItem('nickname')
        window.location.href = '/login'
        return
    }
    // 修改后
    if (res.status === 401 && !isPublicRequest) {
        localStorage.removeItem('token')
        localStorage.removeItem('nickname')
        window.location.href = '/login'
        return { code: 401, mes: '未登录或登录已过期，请重新登录' }
    }

2. 所有页面响应判空（data && data.code === 200）：
    ProfileView（9处）、AdminUserManageView（2处）、LoginView（1处）、
    RecoverAccountView（2处）、RegisterView（2处）；HomeView 原本已有 res && 判空。
    这样即使后端返回异常/空响应，也不抛 TypeError。

3. 弹窗内消息显示（上一轮已修）：注销/换绑邮箱/修改密码/编辑昵称四个弹窗
   各加 modal-msg 消息区，服务反馈显示在弹窗内；handleDelete 失败不再关闭弹窗。

4. send-deletecode 限流放宽（上一轮已修）：@RateLimit maxRequests 1 -> 3，
   与 deleteSelf 一致；per-email 的 setIfAbsent 60s 1 次防刷仍保留。

========== 结果：
- 前端 npm run build 构建通过
- 带有效 token：发送验证码正常（弹窗内显示"账号注销验证码已发送到您的邮箱"）
- token 过期/无效：跳转登录页，显示"未登录或登录已过期，请重新登录"，
  不再误报"网络错误"
- 后端需重启后 authenticationEntryPoint（401 JSON）才生效

========== 教训：
1. request.js 这类公共封装里，任何"提前 return"的分支都必须返回明确对象，
   不能 return undefined——调用方几乎都不会判空，undefined 属性访问必然 TypeError。
2. 前端 catch 里不要把所有异常统一显示成"网络错误，请检查后端服务是否启动"，
   应 console.error 打印原始错误（error.message / error.name），
   JSON 解析失败（SyntaxError）与真正的网络错误要区分开。
3. "前端报错但后端直连正常"的排查顺序：先直连后端确认数据层 OK，
   再读前端公共请求封装（request.js / axios 拦截器）找全局处理逻辑的坑。
4. 401 跳转登录页本身是正常的安全行为，问题在于跳转后的返回值处理；
   涉及登录态的接口，前端要能区分"未登录"与"业务失败"两种响应。
5. 报"网络错误"不等于后端没启动——先看浏览器 F12 Console 里
   "请求失败:" 打印的原始 error，再判断是 401/403/500/解析失败/真断网。
